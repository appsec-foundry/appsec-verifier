# AppSec Verifier: command reference

`appsec-verifier` reads a finished `security-assessment.yaml`, tests the selected findings one at a time against a running target inside an authorised scope, and writes a verification report. It does not re-run or re-score the static assessment. Installation and quick start: [README](../README.md). How the agent and the Verifier's code reach a verdict, with an XSS finding as example: [How verification works](how-verification-works.md). The requirement IDs (VER-…) refer to [`requirements.md`](../requirements.md).

## Commands

| Command | Does | Contacts |
| --- | --- | --- |
| `appsec-verifier ASSESSMENT` | Guided run: asks for the `verify` settings that have no usable default, then runs `verify` (VER-031). | target, model |
| `verify` | Tests findings of an assessment against a running target. | target, model |
| `preflight` | Checks assessment, scope, proxy, source checkout, target, logins and model profile; tests no finding (VER-032). | target, model provider; nothing with `--offline` |
| `scope` | Resolves and validates a scope file and shows what is in and out of scope (VER-001). | nothing |
| `export` | Converts the verdicts of a finished `verification.yaml` into a file meant for AppSec Analyzer, which does not read it yet; no re-verification (VER-021, VER-015). | nothing |
| `update` | Reinstalls a pipx installation of the Verifier after you confirm (VER-033). | the install source, through pipx |

`appsec-verifier` without arguments, or with `--help`, lists the commands with examples. `appsec-verifier <command> --help` lists the options of one command by group, with example calls; `appsec-verifier ASSESSMENT --help` does the same for the guided run. A wrong call shows the short usage, the error and where the examples are. Options count only as written: an abbreviation such as `--show-cost` is an error that names the option meant (`did you mean --show-costs?`), and nothing is contacted.

## Guided run — `appsec-verifier ASSESSMENT` (VER-031)

Called with an assessment and no command, the Verifier reads the assessment offline and shows how many findings it holds, how many of them are candidates for testing against the running app and their severities, and how many lack a code location. It then asks only for what has no usable default. What the selected findings need (a test identity, the proof browser, a marker file, a callback) appears in the test plan of `verify`; `preflight` shows how to provide it.

By default the run tests findings of severity high and above, of every class present, with the profile `claude` and the limits of `data/limits.yaml`. `--min-severity`, `--category`, `--profile`, `--cost-limit`, `--max-calls`, `--max-requests`, `--max-attempts`, `--max-duration` and `--rate` change that. The run prints the selection, e.g. `→ 24 findings to verify, severity high and above (--min-severity to change)`, and repeats the floor in the `Selection` line before the confirmation. If no finding of severity high or above can be tested, it offers the next lower severity that has any, e.g. `Verify the 3 of severity medium? [Y/n]`; no ends the run without contact. A profile that is not available ends the run before any question and names `--profile`.

Enter accepts the default shown in brackets.

| Question | Default | Same as |
| --- | --- | --- |
| Target URL | none; asked only without a scope file (below) | `--url` |
| Identities file | asked only when `identities.yaml` is found next to the scope, the assessment, or in the working directory, and not with `--account` or `--admin-account`; `none` for no identities. A file that starts login programs needs its own `Run them? [y/N]` | `--identities` |
| Allow intrusive probes? | no; asked only when the scope has `allow_state_change: true` | `--allow-intrusive` |
| Existing report in the output directory | asked only when `--output` names a directory that holds a report, e.g. `There is already a report in ./verification. Overwrite it? [y/N]`; no stops the run before anything is contacted. Not asked with `--overwrite` or `--resume`, nor without a terminal, where the run stops as `verify` does. Without `--output` the run writes to a directory of its own (see [Outputs](#outputs)) | `--output`, `--overwrite`, `--resume` |

Each answer goes through the same check as its option and is asked again when invalid: a URL without http or https, with a user name or password, or with an ambiguous path, or an identities file that cannot be used. Options given on the command line are not asked, e.g. `appsec-verifier ./security-assessment.yaml --target http://localhost:3000` asks nothing but the confirmation. A credential variable that the identities file names but the environment lacks is asked for without echo, e.g. `alice: VERIFIER_ALICE_PASS (password_env) is not set; enter its value (hidden):`; Enter alone leaves it unset. The value is kept only for this run, never written and never put into the environment.

A `scope.yaml` next to the assessment, else in the working directory, is used without a question, and the run prints its path. If it cannot be used, for instance because its window has closed, the run stops with exit 2 and says why; correct the file, or move it away to enter a target URL instead. Without a scope file the run asks for the target URL, which has no default and is never taken from the assessment. It then tests only that URL's scheme, host and port, as `verify --url` does without `--scope`, and writes no scope file.

Without an identities file, when the selection holds access-control findings for which the scope declares `test_resources`, the run offers to take the session of each role those resources name from your browser: `Paste sessions for user-a, user-b? [y/N]`. Sign in to the application as that user (a private window or another browser profile for the second one), open the developer tools, copy any request the application sends to the target in the Network tab with "Copy as cURL (bash)", paste it at `Request copied as user-a (hidden; Enter alone skips this role):` and press Enter. The pasted text is not echoed and never run. The run keeps only its Cookie and Authorization headers and refuses a request to another site. When the copied request was a GET, the pre-flight check sends it once with the session to see that it is accepted. Pasted sessions are not renewed, so a session that expires during the run ends that role's tests. The command line printed before the confirmation does not include them; for a repeatable run put them in an identities file with `method: session`.

After the questions the run shows the `verify` settings and the equivalent non-interactive command line, e.g.

```
appsec-verifier verify --assessment ./security-assessment.yaml \
  --url http://localhost:3000 --min-severity high \
  --profile claude --non-interactive --yes
```

and then asks the one confirmation of VER-002 as `[Y/n]`: Enter starts the run. Answering the questions does not confirm. Ctrl-C or end of input at any question stops with exit 2 and contacts nothing.

`--non-interactive` (`--ci`), or standard input that is not a terminal, turns the questions off: `appsec-verifier ASSESSMENT --ci --scope … --profile … --yes` behaves like `verify` with the same options. Without `--scope` or `--url`, or without `--profile`, the run stops with exit 2 and names what is missing; without `--yes` it stops at the confirmation as `verify` does.

## `verify` — verify findings against a running target

`verify` takes the assessment, the scope and limits of the test and a selection of findings, and writes its own report; with `--annotate` also annotated copies of the assessment and of the Analyzer's report.

```
# verify every High+ XSS and access-control finding of an assessment,
# against a local target, capped at USD 5, writing a standalone report
appsec-verifier verify \
  --assessment ./security-assessment.yaml \
  --scope ./scope.yaml \
  --identities ./identities.yaml \
  --url https://localhost:3000 \
  --category xss,access-control \
  --min-severity high \
  --cost-limit 5 \
  --output ./verification
```

A run has five steps:

1. Check the assessment's structure, the scope and proxy settings, the identities file and the model profile (VER-005, VER-032).
2. Resolve selection and scope and, interactively, print both for one explicit confirmation (VER-002, VER-026).
3. Run the checks of [`preflight`](#preflight--check-before-a-run-ver-032): the target answers, the source checkout is readable where `--source` is given, every identity logs in, and the model answers one fixed prompt (VER-003, VER-032). Each check prints one line under `Preflight`, and a failed check stops the run before the first finding (exit 2). These requests count against `--max-requests`, the model test as one call against `--max-calls` and `--cost-limit`. The build check of VER-003 is not implemented yet.
4. Test each selected finding, bounded and inside the scope (VER-008, VER-015, VER-017).
5. Write the report with its evidence and, with `--annotate`, the annotated copies (VER-020, VER-022, VER-027, VER-038).

Before the confirmation, `Test plan` names how many of the selected findings the run will test, with the number of runs their variants add, and lists them, one line each with severity, class, title and the requests the assessment names for it (for example `GET /rest/basket/:id`), with `(prepares)` for the setup of a test resource, or `no request in the assessment`. Where the finding's text names no request with a method but a URL with a query, such as `a link to /vulnerabilities/xss_r/?name=…`, that URL's path counts as a GET. A finding in a page script that names no request shows `no request in the assessment; its file path may name one` (see [Continuous control](#continuous-control-ver-036)). `page /#/search` is a browser route. A finding whose declared variants differ in request or inputs names no request on its own line and adds an indented row per variant with its request and the inputs it names, such as `q (query)`, in the order the runner tries them; the first confirmed variant retires the rest. Variants alike in both get no rows: the finding's line names their request and their count. On a terminal `verify` cuts a line to the terminal's width; `preflight` shows it whole. The agent gets these requests and the finding's scenario and attack steps; it reads source code only with `--source`.

`Not testable` groups the findings this run cannot confirm by what they need, with how to provide it:

| Need | When |
| --- | --- |
| test identity | an access-control finding, or one whose named requests all need a login |
| access request | an access-control finding without a `test_resources` entry whose named requests allow none of the [proofs](#proof-per-class-ver-009-to-ver-013): a GET for the comparison with an `--admin-account` (not for an IDOR, CWE-639), or a write that creates a record (one that names no existing record in its path) together with a GET or a write that changes the record by its identifier. DELETE is never sent. |
| proof browser | XSS |
| marker file | path traversal |
| callback | SSRF |
| injection contract | an injection finding with no request and no `--source` to derive one; `injection_inputs` can supply the input explicitly |
| request information | the assessment names no request for the finding and there is no `--source` to read one from. `--source` can resolve a literal route at the finding's evidenced source location, one another file registers for its handler, or, for a page script, a page its file path gives (see [Continuous control](#continuous-control-ver-036)); an access-control finding can name its request in a `test_resources` entry instead. |
| intrusive mode | every named request writes, or, for a finding that names none, every route `--source` registers for its handlers (see [Continuous control](#continuous-control-ver-036)), or, without a `test_resources` entry, an access-control finding that only a record an account creates can prove: an IDOR (CWE-639), and any other one without an `--admin-account` |
| test capability | the reported variants need unavailable tools and neither a source checkout nor a declared read request permits diagnosis for a supported alternative; a variant that needs a header has it when the run has a test account, whose session sends the authentication header, unless the header is one of the variant's inputs |
| repeatable request | every request an injection finding names writes, and its `injection_inputs` entry, if any, declares no query parameter that a GET on its path would carry. The proof sends each control twice but never repeats a write, so `--allow-intrusive` does not help. |

`verify` names what to provide in a few words, one line per need; `preflight` shows how, with the lines to copy into a scope file. These findings are not tested and appear in the report as `not-attempted` with the reason; `--test-all` tests them anyway. When nothing is left to test, the run stops with exit 2, contacts nothing and writes no report. What `verify` prints while it runs is described under [Console output](#console-output).

### Input and target boundary

| Flag | Meaning | Req. |
| --- | --- | --- |
| `--assessment PATH` | `security-assessment.yaml` to verify, as the Analyzer wrote it. | VER-005 |
| `--scope PATH` | Authorisation scope file (`schemas/scope.schema.yaml`): the target boundary, the declared proxy and auth hosts, the test window and the owner. Without it, `--url` alone sets the boundary. | VER-001 |
| `--url URL` (alias `--target`) | Start URL of the target. With `--scope` it must fall inside the scope, and without `--url` the scope's `base_url` is used. Without `--scope` it is required and is the whole boundary: its scheme, host and port, with no window and no owner. | VER-001/004 |
| `--identities PATH` | Test identities (`schemas/identities.schema.yaml`): per role a bearer token, basic, form, copied browser headers, an OIDC flow or a login program. Secret values come from environment variables, or are asked hidden in an interactive run, never from this file. | VER-016/028/040 |
| `--account USER[=VAR]` | A test account by user name, instead of `--identities`; repeat it for a second account. The password comes from the variable `VAR`, or is asked hidden. See [Test accounts on the command line](#test-accounts-on-the-command-line-ver-041). | VER-041 |
| `--admin-account USER[=VAR]` | A privileged test account. It sends only GET, HEAD and OPTIONS, also with `--allow-intrusive`. | VER-041 |
| `--login-url URL` | Where `--account` and `--admin-account` sign in. Default: the login entry point the assessment names for the target, else the login form the target URL leads to. | VER-041 |
| `--source DIR` | Checkout of the application's source code. The agent may read it, search it by file name or path before reading so it does not guess paths, and search file contents for a literal string of 3 to 200 characters, which returns at most 40 matching lines, each with its path and line number and cut to 200 characters, and after them up to 40 further files with the number of their matching lines not shown, a directory with more than three such files as one entry with their count; never `.env` files, keys, credential stores, `.git/`, vendor directories, binary files or files above 1 MiB. A path that is not a readable directory stops the run before anything is contacted (VER-032). | — |
| `--proxy URL` | *Not implemented yet; set `proxy.url` in the scope file.* Route target and auth traffic through this HTTP(S) proxy, overriding the scope's `proxy.url`. Proxy credentials still come from the variables the scope names. | VER-029 |

### Select what to verify (VER-026)

All selectors read from the assessment and combine with AND. Without a selector the run verifies every finding that can be tested dynamically (VER-006) and says so before it starts. Prefer categories and severities over CWEs.

| Flag | Meaning |
| --- | --- |
| `--category LIST` | Classes or finer techniques: `access-control`, `idor`, `sqli`, `nosqli`, `xss`, `path-traversal`, `open-redirect`, `ssrf`, … So `--category idor` verifies IDOR alone. `quick` selects the findings the Verifier can confirm cheaply (see below). The guided run names the classes the assessment holds. |
| `--severity LIST` | Exact severities, e.g. `critical,high`. |
| `--min-severity LEVEL` | Severity floor: `low\|medium\|high\|critical`. |
| `--strict-severity` | Keep the floor exact: add no findings below it (see below). |
| `--only ID[,ID]` | Specific finding ids, e.g. `T-037,F-001`. Overrides the other selectors. |
| `--class LIST` | (advanced) Weakness classes. |
| `--cwe LIST` | (advanced) Specific CWEs, e.g. `CWE-79,CWE-639`. |

With `--min-severity` and without `--strict-severity`, up to eight findings below the floor are added within the other filters: declared prerequisites of selected findings, and access or exposure findings on `/actuator`, `/management`, `/admin`, `/metrics` or `/debug` routes. Health, readiness and liveness routes do not qualify on their own. An added finding that lacks an operator resource is still not tested.

The category `quick` holds the findings the Verifier can confirm cheaply: XSS, and SQL or NoSQL injection (CWE-89, CWE-943), whose request the assessment names and a read can send, such as `GET /rest/products/search`. A finding that names no request, or only writes, is not `quick`. With `--min-severity` or `--severity` and without `--strict-severity` or `--only`, every `quick` finding of another severity is tested as well, within the other filters and without a cap. It is ordered by its own severity, so under a severity floor it runs after the selected findings and a limit stops it first. The settings line counts them (`with 2 quick below it`).

The test plan names each addition and its reason before the confirmation. `--only`, category and CWE filters stay strict.

The selected findings are tested most severe first. Within one severity, findings whose named request a read can send come first, then findings whose named requests all write, then findings the assessment names no request for; the finding number breaks the remaining ties, and the variants of one finding stay together, those that need no write first: a variant needs one when its request writes or it lists the capability `state-change`. A run stopped by a limit has spent its budget on the highest-severity findings it could reach. A finding can name prerequisites with `verification_dependencies: [T-002]` in the assessment; selected prerequisites run before the findings that depend on them, ahead of the severity order. Only these explicit dependencies set an order, and cyclic dependencies establish none. A prior result covers only its own requests, so verified findings do not establish a complete attack chain.

### Boundaries — cost and load (VER-015)

| Flag | Meaning |
| --- | --- |
| `--cost-limit USD` | Model spend for the run. Reaching it stops the run (exit 3), in a terminal after the question below, and so does a model call that reports no usable cost. Rejected with `codex-cli` and `copilot-cli`, which report no cost. |
| `--max-requests N` | Total requests to the target. Refused requests are not counted. |
| `--max-attempts N` | Agent steps per finding; each step is one model call that proposes a tool call or the verdict. Default 12. Reaching it ends unfinished testing with `limits_hit: attempts`; a previously checked result survives an unfinished QA follow-up, with its open objections. |
| `--max-calls N` | Model calls for the run, for every profile. |
| `--max-duration S` | Run time in seconds. |
| `--rate RPS` | Requests per second to the target and its login endpoints, redirect hops and the proof browser included. `0` turns the rate limit off. |

The defaults are in `data/limits.yaml`. Every limit must be greater than 0; only `--rate` accepts 0. A negative or zero limit, or a key in `data/limits.yaml` that the Verifier does not enforce, blocks the run (exit 2) before anything is contacted.

When the cost, request, call or time limit or the end of the scope window is reached, unfinished testing ends `inconclusive` or retains an already checked result with unresolved QA objections, the remaining findings are reported `not-attempted` with the limit in `limits_hit`, no further model call is made, and the run exits with 3. After three failed model calls in a row, for example an exhausted quota or a rejected key, the run makes no further model call and the remaining findings end `inconclusive` with the reason.

A failed request is not retried. Only GET, HEAD and OPTIONS may be resent once after a 401 and a session renewal; POST, PUT and PATCH are never resent. Each answer is read for at most 30 seconds and up to 10 MiB after decompression; a slower or larger answer ends that request with an error the agent sees.

In an interactive terminal, a run that reaches its cost limit first asks: `New total cost limit in USD (more than 10.40), or Enter to stop testing:`. Type the new total, not the amount to add, for example `20` to raise a limit of USD 10 to USD 20; the run then goes on with the finding it was testing, and the limit per finding (`finding_cost_fraction`) grows with it. Enter, the end of input, three invalid answers or the end of the run time keep the limit; the run then stops as above and does not ask again. Keys pressed before the question appears are discarded. A run asks at most 16 times, and the time spent waiting for your answer counts toward `--max-duration`. The request, call and time limits are never raised this way. There is no question with `--non-interactive`, `--json` or without a terminal. The report names each raise (`Cost limit` under the run facts, `meta.limits.cost_limit_raises` in `verification.yaml`); `--resume` uses the limit of its own command line.

Ctrl-C stops the run: the finding under test ends `inconclusive`, the remaining ones are `not-attempted`, the report is written with the results so far and `meta.interrupted: true`, and the run exits with 130.

### Continuous control (VER-036)

Before each model call and each tool action, the Verifier checks the remaining run time and the scope window. When either runs out, active work stops; recorded exchanges still save within five more seconds, and a screenshot timeout keeps the verdict and the recorded evidence. These deadlines need POSIX timers in the main thread; where they are missing, for example on Windows, active verification stops. Offline commands work everywhere.

Each request must match an assessed or operator-declared route, or a related request independently checked against recorded evidence. With `--source`, a literal `get('/route', ...)`, `app.get` or `router.get` declaration up to 40 lines before the finding's evidenced location can supply an initial route. When the assessment names no route, a route another file registers for a handler of the finding's file can supply it too. The registration is a method call on `app`, `router` or `blueprint`, a Django `path()`, or a mount with `app.use` or `app.all`; it must name `alias.handler`, where `alias` imports the finding's file in that file (`import * as views from './views'`, `from pkg import views`) and `handler` appears in the finding's file, or a handler that file imports by name from the finding's file, such as `getUserProfile` after `import { getUserProfile } from './routes/userProfile'` or `from .views import detail`. A mount answers every method below its path, middleware included, so it counts only for the function that holds the finding's evidenced line, such as `app.use('/keys/:file', serveKeyFiles())` for a finding inside `serveKeyFiles`. The Verifier looks for such registrations in the source checkout before the agent starts, in whole files, and offers up to four of them to the agent, those of the function that holds the evidenced line first; the agent can also derive one from a step that read the registering line. The report names the file and line each came from. In safe mode a finding is not tested when every route found this way writes, as for a finding whose named requests all write. A finding in a directly served script or page (`.php`, `.phtml`, `.jsp`, `.jspx`, `.asp`, `.aspx`, `.ashx`, `.cfm`, `.cgi`, `.pl`, `.html`, `.htm`) that names no request and whose file declares no route up to 80 lines before its location can take its request from its file path (VER-056). The candidates are the file's path below the web root (the repository root, or below a directory such as `public`, `htdocs`, `www` or `src/main/webapp`) and up to two directories above it, never `/` itself; the agent learns them and reads them with prerequisite GETs. A successful answer of the file itself makes it the request, with the names the file contains as its inputs. A page above it supplies the request through its own forms and links that stay in its directory and carry an input the file contains as a literal, as `id` in `$_GET['id']`. No other link is followed. The agent can also derive requests from recorded source declarations or application links and forms, up to eight per finding variant together with those the Verifier resolved, as described under [Test planning](#test-planning-by-the-agent-ver-043). Requests stay on the target origin and within scope. A request carries an input the finding declares in the path, such as `id` in `/rest/basket/{id}`, with the value in that segment, as `/rest/basket/2` does. The code still checks methods, identities, markers, operator-declared resources and injection inputs. When the Verifier creates a resource itself, only the owning account may perform its preparation writes. Where a finding's own request needs a value the assessment does not name, such as a CSRF token or a CAPTCHA id, the agent may first fetch it with a read-only GET on the target origin, up to three such reads per finding; the report lists each one. A prerequisite read is never a proof, and a finding whose prerequisite cannot be obtained is reported as untested.

The same read request may run twice per finding, so proof controls can be repeated; the same write request runs only once. An injection experiment's generated controls keep a repetition budget of their own per accepted plan, so a corrected plan starts fresh rather than inheriting an aborted one's spent budget, and a finding runs at most three experiments. Three tool errors or HTTP server errors in a row end the finding `inconclusive` with `limits_hit: stagnation` and the reason `stopped: three actions in a row failed …; the last: …`, which names the last failure, and other findings continue. A finding's model spend is bounded the same way: once it reaches its share of the run's cost ceiling, a quarter by default and never below a floor, it ends `inconclusive` with `limits_hit: finding-cost` and the next finding is tested, so one finding cannot drain the run; `finding_cost_fraction` and `min_finding_cost_usd` in the limits file set the share and floor, and a zero share turns it off. `--max-attempts` counts both model decisions and HTTP or browser actions per finding; browser resources and logins count against `--max-requests`. Source files and agent CLI outputs larger than 1 MiB are not read.

| `--report` | Write a standalone report and leave the assessment untouched. Default. | VER-020 |
| `--print` | List every finding in the results at the end, unsupported or incomplete ones included, with the whole reason. | VER-013 |

| `--read-only` | No write requests, even with `--allow-intrusive`, and no question for them. | VER-014, VER-052 |

| `--profile NAME` | Model profile (below), as in AppSec Analyzer. Default `claude`; required with `--non-interactive`. | VER-023 |
| `--model NAME` | Model for the selected profile; default is the profile's model. | — |

Whatever the profile, the model only proposes the next step as one JSON object, and the Verifier checks it against strict schemas and runs it with the same scope-guarded tools (VER-017, VER-019). Nothing invalid runs. A tool call whose arguments are not one JSON object or break its schema goes back to the model as an error and counts as a failed step; any other invalid step, such as an unknown action or an invalid verdict, ends the finding `inconclusive`. They get only the environment they need: no identity secrets and no API keys of other providers. For `claude` and `codex-cli` each call is also checked for tool use; a session that offers or uses a tool ends the finding `inconclusive` and stops all later model calls of the run. Copilot CLI prints only the answer, so its isolation rests on the pinned version and its flags. `codex-cli` and `copilot-cli` have only been tested with simulated answers.

### Test planning by the agent (VER-043)

Declared variants identify the finding's starting hypotheses; they do not require a finished exploit recipe or exhaust its possible approaches. Each variant is tested separately, until one confirms the finding; a variant whose request another variant already tested is not tested again. No test plan is required. A confirmation counts when recorded steps meet the proof of their class, whether they were sent before or after any plan. Steps sent under a plan are checked against that plan; one accepted after them, for example after a QA question, does not replace it. A confirmation cites the steps of one experiment; an injection's negative verdict cites experiments in at least two contexts (see Negative verdicts below). The agent declares only what the Verifier must generate itself: an injection experiment's input and template, or an access-control marker; for an injection experiment that declaration still comes before its controls, because the Verifier generates them (VER-011). When a tool result reports `proof_ready` with the steps that already satisfy the proof, the agent submits a confirmed verdict citing them; this happens for an executed XSS marker on the finding's route, an SSRF callback hit, a redirect to the marker host and a marker-file read. When a confirmed injection verdict cites no steps or steps that fail, and the latest experiment the Verifier ran reported that its proof holds, the Verifier checks and records that experiment's steps instead. A negative result needs attempts after its plan. The console shows one line per accepted plan, and the report's appendix keeps any declared plans under `Test plan`.

When a verdict lacks the evidence its class requires, the agent may correct its experiment within the remaining step, request and model limits, in at most two correction rounds. A claim that stays unproven ends `inconclusive`, with the missing evidence in the report.

The assessment's optional `verification_context` (version 1) gives per variant the input locations, query construction, dialect and driver where known, processing and filter order, controls, prerequisites, observations, negative controls, unknowns and sources. The agent reads it on demand, together with the older mechanism traces, scenarios, attack steps and evidence, each within a size limit. Assessments without it remain readable. This context supplies hypotheses, never authorisation to test. Custom request headers and browser clicks are unsupported. A declared read request or `--source` still permits bounded diagnosis for a supported alternative; the unsupported plan itself remains refused. Form bodies are supported with POST, PUT and PATCH in intrusive mode.

The agent may use `derive_request` to cite an earlier source or HTTP step and propose a method, path and input names. Source evidence must be the finding's evidenced file or a local import followed from recorded source, with at most three import levels. A declaration counts by its form, whatever the framework: a route literal as the first argument of a call or annotation that names an HTTP method or a routing function, such as `router.get('/x', …)`, `r.GET("/x", …)`, `Route::get('/x', …)`, `@GetMapping("/x")`, `@RequestMapping(value = "/x", method = RequestMethod.POST)`, `[HttpGet("x")]`, `@app.route('/x', methods=['POST'])` or Django's `path('x/', …)`; one that names no method stands for GET, and a plain method call such as `config.get('key')` counts only with a slash in its literal. The route may carry a prefix declared above it in the same file, also in another read of that file: a class-level `@RequestMapping("/api/files")` or `[Route("…")]`, a `prefix=` or `prefix(…)` argument, or a route `Group("…")`. A request input counts when the handler's lines up to the next declaration name it, a path input when the route has its placeholder. A complete successful HTTP response can supply HTML form actions, input names and links. Every derived request must stay on the original route or its immediate collection, record or view; generic roots such as `/api` do not permit crawling, and derived routes never expand that resource boundary. Without any assessed route, only a declaration at most 80 lines before the evidenced source location can establish the initial resource. Unrecognised syntax or ambiguous relationships remain unresolved. Derivations and their supporting step numbers are recorded; operator restrictions and proof rules take precedence. When a finding's request needs a value the assessment does not name, such as a CSRF token, a CAPTCHA identifier or a nonce, the agent may first fetch it with a GET within the scope, in any mode and with at most three different reads per finding; such a read is never the tested operation and never part of a proof (VER-047). The same reads serve the candidate pages of a page script (VER-056) and share that allowance.

With `read_response` the agent can inspect or compare a JSON field or a window of 1,500 characters in this finding's recorded, redacted responses without sending another request. Up to 64,000 characters per response and 256,000 per finding are kept for this; a truncated body cannot support a field comparison.

### Proof per class (VER-009 to VER-013)

A `confirmed` verdict must name the steps that prove it in `proof_steps`, with step numbers as in `agent-log.jsonl`. The Verifier checks them in code against what its tools returned; evidence the model lists itself is never taken over. When the check passes, the Verifier adds the record it checked: for access control, injection, open redirect and path traversal `evidence/<finding>-exchanges.json` (owner-only), with method, path, parameters, body, identity, status, length and a hash of the redacted response body per cited step; for SSRF `evidence/<finding>-callback-hits.json` with time, method and source address of each hit.

**Access control (CWE-639, 862, 863, 285, 306, 200, 497, 530, 538, 548, 552).** With a `test_resources` entry from the scope, the same method, path and inputs must return the entry's harmless marker both to an allowed role and to a denied role with independent credentials. Two successful responses alone do not establish unauthorised access. A `test_resources` entry always takes precedence and gives confidence `high`. For missing authentication (CWE-306) and exposure findings (CWE-200, 497, 530, 538, 548, 552) the agent's own requests reach only such an entry; without one these findings are proven only by the comparison without credentials below. Without an entry, the other findings (CWE-639, 862, 863, 285) can be proven in four more ways, the IDOR (CWE-639) only in the first two, each with confidence `medium`:

- Own resource, with two normal accounts and `--allow-intrusive`: the Verifier draws a random marker for the finding. One account, the owner, creates a record that holds the marker with one write to a route of the finding that names no existing record in its path, such as a POST to a collection, and reads it back. The same GET without a login must not show the marker; otherwise the resource is public and the finding stays `inconclusive`. If the other account's GET shows the marker, the finding is `confirmed`; 403 or 404 gives `blocked-by-control`. Only the owner may send the marker, and a read that sends it does not count. The created record stays on the target; the report gives its marker under `proof.marker`.
- Write on the own resource, with the same accounts, for a finding whose request changes a record by its identifier, such as `PUT /api/Feedbacks/:id`: the plan names that request as its change, and the Verifier draws a second marker. The owner creates the record as above and reads it back. Once the owner's read has shown the first marker, the other account sends the change with the second marker to the identifier the creating answer returned (in the `id` field of the answer or of its `data` wrapper, or in the `Location` header); any other identifier is refused, also that of a record nested in the answer, such as its owner. If the owner's next read shows the second marker, the finding is `confirmed`; if the change was answered 403 or 404 and the read still shows the first marker, it is `blocked-by-control`. When the finding names no GET request, the record is read with GET on the path of the change, and only that record. A finding variant whose request is the write is tested this way: the plan reads with GET and names the variant's request as its change. Without a request that creates a record and one that changes it, this proof is not available. The record stays on the target; the report gives both markers under `proof.marker` and `proof.second_marker`.
- Privileged function, with an `--account` and an `--admin-account`: when the privileged account gets a 2xx answer with content, the same GET without a login gets 401 or 403, and the normal account gets the identical answer, the finding is `confirmed`. 403 or 404 for the normal account gives `blocked-by-control`; any other answer stays `inconclusive`. The answers are compared as received, before credentials and user names are redacted, so an answer that names the signed-in user or holds that user's credential never counts as identical, while a list that names every user can. The finding supplies the intended privilege restriction; matching responses do not establish it independently. The report states this assumption. This proof fits only a finding that names a privileged function, so an IDOR (CWE-639), which concerns another account's record, never takes it. When the request without a login gets the content, the agent is told at once that this comparison cannot confirm and that the comparison without credentials can. Another account's record without `--allow-intrusive` needs a `test_resources` entry.
- Comparison without credentials (VER-057), with any account of the run, also in safe mode, for every finding except an IDOR: the agent names the finding's GET as one concrete path, with query inputs in `fixed.params`, and the account. The Verifier then sends three requests itself: the GET as the account, the same GET without a login, and a GET without a login to a random path next to it (the last path segment replaced by one that starts with the finding's marker, such as `/rest/admin/vrf1a2b…` for `/rest/admin/application-configuration`). When the account gets a 2xx answer with content, the request without a login gets the identical answer, and the random path does not get that answer with a 2xx, the finding is `confirmed`. The random path shows a target that answers every path alike, such as a single-page application, which then confirms nothing. The answers are compared as received, by a keyed hash held in memory; their bodies reach neither the model, the log, the proof of concept nor a screenshot, which matters for keys, logs or configuration with secrets. An answer that changes between requests, such as metrics with counters or a log listing with file sizes, or that names the signed-in user, is never identical, and the finding stays `inconclusive`; a `test_resources` entry with a stable text of that answer can prove it instead. The finding supplies the intended restriction, and the report states this assumption. The comparison supports no negative verdict: a refusal without a login says nothing about a control the finding is about.

Roles with the same name and the same session never count as two accounts. For the preparation request the Verifier can add for these proofs, see [Runtime candidates and test preparation](#runtime-candidates-and-test-preparation).

**Archive-upload traversal (CWE-22).** An `archive_checks` entry declares the finding, evidenced POST upload route, multipart field, isolated test extraction directory and read URL for a file in its parent directory. The operator must ensure that URL maps to the parent directory, outside the extraction directory, and that both are disposable test locations. The `archive_probe` action first requires a 404 or 410 at the generated marker URL, then uploads one ZIP containing only `../<marker>.txt` or `../<marker>.md`, matching the declared read URL, with a fresh harmless value, and reads the declared URL. Only an exact fresh value after a successful upload confirms escape. A successful upload alone proves nothing. Intrusive mode and scope permission for state change are required; privileged accounts cannot upload. One upload is attempted per finding, including when the response is lost; it is never retried automatically. A declared cleanup endpoint receives one POST with the marker filename, followed by a read checking absence. Otherwise cleanup is `manual-required`; failed or interrupted cleanup is recorded too. No DELETE is sent. The fixed requests count against the run's request and time limits. Other archive formats, deeper paths, arbitrary content and automatic filesystem discovery are unsupported.

**Injection (CWE-89, 943, 78, 94, 95, 1336, 643, 90).** The Verifier generates the controls itself. The agent chooses the input to treat as literal data from an assessed or evidence-derived request (a query parameter or JSON field of a read request, a body field of a write in intrusive mode, or an evidenced path segment under VER-044); a scope entry in [`injection_inputs`](#scope-file--scopeyaml-authorisation-ver-001) pins it instead, and takes precedence. The pin separates injection from an intended calculator, template editor or query language; fresh observations must still prove evaluation. The agent declares the hypothesis, the one input to change and the observation before collecting evidence. A working baseline, a true condition and a false condition are each repeated at least twice, with all other inputs and the identity fixed. The selected observation must be stable and separate into two classes: the true condition and its complement share one observation, the false condition and its complement another, and the true class need not match the uninjected baseline. It may be a response field, also one that only the true class's answers contain while the false ones lack it, or, for a result set, the container itself. For a page or text answer the plan gives `text` instead of `pointer`: a literal that a recorded answer shows and no sent value contains, present for one class and absent for the other. An arithmetic plan without either finds each control's own result in its answer as a whole number that neither the baseline's nor another control's answer holds (VER-055). A timing experiment never confirms injection, however clear the delay; it can only support a negative verdict, when all responses are identical successful answers within 0.5 seconds of each other. Reflected input, status changes, generic errors and ordinary search differences never confirm injection either, and citing one request several times does not count as a repetition. When a read plan is accepted the Verifier runs its controls at once, twice each, within the request, time and step limits, and reports whether the proof holds; the agent then submits the verdict without a separate step. A read plan with controls the agent chose itself, without a template, runs the same way; such controls can support a negative verdict, never a confirmation, and the report to the agent names the declaration that could confirm the finding through that input, or says that none can. They carry no values in `fixed`: a plan that gives some is refused and names the declarations whose controls take them. `sql_template` and `expression_template` may be a list of up to three candidates: the Verifier runs the first and, when one of its controls meets a server error, the next, each as an experiment of its own within the finding's three, until the proof holds or the candidates run out. A failed control is named in the report to the agent with its step, status and an excerpt of its error, and a proof that is still short says how many of each control are recorded. A write-only injection finding is tested only in intrusive mode (`--allow-intrusive`). There the plan's acceptance sends nothing; the agent asks with `send_controls`, and the Verifier sends the generated controls in one step, each twice, an auth-artifact control once, and stops at the first control that fails. It does so once per accepted plan and never for a candidate template the agent has not seen: a write uses the first template, and another one needs a revised plan. Each control carries the declared input and, unchanged, the values the plan gives the request's other inputs in `fixed` (`params`, `json` or `form`), such as the password next to a login's user name; a plan whose controls would lack an input the finding's variant declares is refused and names that input. The scope file may also forbid writes with `allow_state_change: false`. A path input retains its whole-segment template and travels in `path_inputs: {name: "value"}`; the tool encodes it and the scope guard checks the resulting URL. This explicit input API supports one placeholder, without a query or fragment in the template. NoSQL operator controls still require JSON input. Per mechanism:

| Mechanism | Plan | Controls |
| --- | --- | --- |
| SQL (CWE-89) | `sql_template` with one `{{predicate}}` placeholder | fresh complementary true and false predicates |
| NoSQL (CWE-943) | `operator_challenge: nosql` with `input_location: json`, or `params`, where the controls travel in bracket notation (`q[$eq]=…`, `q[$in][]=…`) for a target that builds an object from it, such as Express 4 or PHP | a literal baseline lookup against fresh equality and membership operators, ten recorded requests |
| NoSQL in a server-side JavaScript predicate such as `$where` (CWE-943) | `js_predicate_template` that starts with a `baseline` finding a record and joins one `{{predicate}}` placeholder with `&&`, without `||` | fresh complementary JavaScript predicates; the true ones repeat the baseline's answer, the false ones suppress it, so no control returns more than the baseline's record |
| LDAP (CWE-90) | `predicate_template` with one `{{predicate}}` placeholder and an evidenced `predicate_attribute` | complementary filters that repeat the baseline for true predicates and suppress it for false ones, ten recorded requests |
| Command, code evaluation, template, XPath (CWE-78, 94, 95, 1336, 643) | `expression_template` with one `{{expression}}` placeholder | fresh arithmetic expressions whose products and sums are returned as the selected JSON value or, without `pointer`, each in its own answer |
| Out-of-band (CWE-94, 95, 1336) | `oob_template` with one `{{callback}}` placeholder | the injecting payload reaches the callback listener, the same URL sent as inert data does not |
| Auth artifact (CWE-89, 943) | `auth_artifact: true` on a `sql_template` or `operator_challenge` challenge, with a `pointer` | the true-predicate controls yield an authenticated artifact, the false ones and the baseline do not |
| Returned marker (CWE-89) | `sql_marker` with a punctuation-only `prefix`, the UNION `columns` and the marker `column` | a UNION the Verifier builds returns its own concatenated marker constant through the query channel for one control, not for its complement |
| Engine error (CWE-89, 643, 943, 94, 95, 1336) | `error_probe: true`, with a `baseline` for every class but NoSQL | the Verifier's per-class set of syntax-breaking metacharacters, each with a balanced counterpart; at least one break raises a backend engine error its counterpart does not |

Command templates are limited to a plain baseline followed by `; printf '%s' "$(({{expression}}))"`; other commands and extra inputs are refused.

When an injection surfaces no response difference, an out-of-band proof confirms it instead. The agent declares an `oob_template` with one `{{callback}}` placeholder; the Verifier substitutes the listener's URL and builds two controls: the injecting payload, and the same URL as bare data. A confirmed proof needs the injecting control to reach the listener at least twice, each with its own fresh marker, while the bare-URL control does not, which separates injection from an ordinary URL-fetching feature. Only a nonce returns, so no application data is read, and the payload may carry a URL only to the listener. This needs a callback listener (as SSRF does) and, on a write, `--allow-intrusive`. A standard run uses it only for code-evaluation and template injection, where no response-side proof exists; SQL, NoSQL and XPath keep the response-side forms above, and command execution as the carrier is out of scope.

A login-bypass SQL or NoSQL injection shows no response-field flip but a change in authentication: the true predicate logs in, the false one does not. Set `auth_artifact: true` on the boolean challenge and point `pointer` at the authenticated artifact, such as a session token field. The Verifier confirms when the generated true-predicate controls yield that artifact and the false-predicate controls and the baseline do not; the uniform-status rule does not apply, since a 401-to-200 flip is the signal, and no repetition is needed because the complementary true and false pair rules out a coincidence, so each control is sent once. A response-field plan whose controls show such a flip is told to use this form instead. The artifact's presence is read in code; its value is withheld from the recorded body, the excerpt and the hash, so no token reaches the model or the logs.

For SQL, XPath, NoSQL, template and code-evaluation injection the recommended first step is an engine-error proof: set `error_probe: true`. The Verifier sends its own per-class set of syntax-breaking metacharacters, each paired with a balanced counterpart, and confirms when at least one break raises a backend engine error (a SQL, NoSQL, XPath or template-engine parser error) its counterpart does not, classified in code against a generic failure or a validation message. The sets are `'`, `"` and the backtick for SQL, `'` and `"` for XPath, the delimiters `${`, `{{`, `<%` and `#{` for template and code-evaluation injection, and an unbalanced `$regex` group for NoSQL; every class but NoSQL appends the break to a `baseline`. LDAP keeps its result-set contrast, since a malformed filter usually returns empty, and command execution has no engine-error form. A break the target appears to filter may be resent in a harmless alternative representation. On a write the controls carry the finding marker, so they stay attributable. The error text is kept only in the owner-only proof of concept and never reaches the model, which sees only the error class.

A returned-marker proof declares `sql_marker` with a `prefix` of punctuation and whitespace that closes the current literal and parentheses, the UNION column count and the column that carries the marker; the Verifier builds the UNION and a marker constant of its own, two halves the database concatenates, and confirms when each control's marker returns through the query channel and the complement's does not. The Verifier owns the SELECT list and the marker is its own constant, so no real column or row is read, and an echo of the payload cannot reproduce the concatenated value.

**XSS (CWE-79).** A `browser_check` in which the marker executed. Each finding gets a random two-part marker. The payload must call `alert('<part1>'.concat('<part2>'))`, without `+`, which many applications read as a space in a query string, and only a dialog showing the joined value counts, so a page that merely echoes the payload text is not taken for execution. If any request of the probe carried the joined value itself, also percent-encoded, the dialog does not count either: a page that shows a parameter through `alert()` by design would display it without any injected script. Execution must happen in the checked page's main frame and origin, without a sandbox response policy; execution in a child frame stays unconfirmed because its permissions are not established. A `confirmed` XSS verdict without such an executed marker becomes `inconclusive` ("indicative, not executed"), whatever the model says. If the marker did not execute but the browser found a part of it in an injected `<script>` element or event-handler attribute on the finding's route, for example because a content security policy blocked it, the label is "indicative: breaks HTML context" instead: the payload left its HTML context, but no execution was shown, so it is still not a confirmation. A marker in ordinary text or a plain attribute value does not count. On execution the browser saves a JSON event record under `evidence/` (owner-only) and, unless `--screenshots` leaves out `xss`, a screenshot.

The proof browser is headless Google Chrome (Playwright, `appsec-verifier[browser]`; `--headful` shows it). Chrome opens no connection itself: every request of the page goes through the same scope check, limits and safe mode as the agent's HTTP requests, identity headers are added only for the identity's origin, redirects go back to the browser so each hop is checked, and anything else is aborted, service workers included. WebSockets are never connected. Chrome runs in a network namespace of its own (`unshare --user --net --map-current-user`) with only a loopback interface, so traffic the interception never sees, such as WebRTC over UDP, cannot leave the machine. This needs Linux, `unshare` from util-linux and unprivileged user namespaces, and Chrome runs with its own sandbox. Without Playwright or Chrome, or where the namespace or the sandbox is unavailable (other systems, some containers), the browser does not start and XSS findings cannot be confirmed. Without Playwright or Chrome the `Browser` line in the run settings says so; the line also names the classes that get screenshots. If Chrome fails during the run, that check ends with an error the agent sees, and the next check starts a new Chrome. Each page check is time-bounded; a page that does not answer in time keeps its proof of execution but gets no screenshot.

**Open redirect (CWE-601).** A cited request answered 301, 302, 303, 307 or 308 whose `Location` leads to `<marker>.invalid`, a host drawn at random per finding. `.invalid` never resolves (RFC 6761). Redirects are never followed: a 3xx answer comes back with its `Location`, and a next hop is a request of its own.

**Path traversal (CWE-22, 23, 73).** A cited request whose response held the content of the scope's `marker_file`. The model is told the file's path, never its content, which shows as `[marker-file]` in every tool result. A request that itself carried the content does not count.

**SSRF (CWE-918).** A request with the finding's marker reached the callback listener; no `proof_steps` are needed. Each request gets a fresh marker, and only hits within that attempt's observation window count. A hit proves that retrieval, not that arbitrary internal addresses are reachable. To confirm, the scope must also set `callback.expect_rejected: true`, which states that fetching this destination violates the intended access policy; an intended URL-fetch feature is no SSRF. Without it a hit is recorded as retrieval observed and the finding stays `inconclusive`. The listener the Verifier starts by itself for a `localhost` target needs no declaration: it is on a loopback address, and an application that fetches a loopback URL it was given has reached an internal address.

Path-traversal and SSRF probes may aim only at these markers. In a path-traversal probe, a parameter or body value that names a file (it contains `..` or a NUL, or starts with `/`, `\`, `~` or a drive letter) must name the marker file; without `marker_file` in the scope no such value is sent. The traversal goes in a parameter or the body, because dot segments and encoded separators in the URL path are refused. In an SSRF probe, a value that holds a URL (`://` or a leading `//`) must point at the listener's origin. An out-of-band injection probe is steered the same way: every URL embedded in its payload must point at the listener's origin. These rules also apply to query parameters written into the URL. Values are percent-decoded up to three times before the check; other encodings a target may accept are not decoded, and the agent is told the same rule.

The listener binds only to a loopback `callback.host`. When the target is on `localhost`, `127.x.x.x` or `[::1]` and the scope declares no `callback`, the listener binds to a free loopback port by itself, and the run settings say so. That works only when the target reaches this machine's loopback, e.g. a process started directly or a container run with `docker run --network host`; with `docker run -p` the container's `localhost` is the container itself, and SSRF findings stay `inconclusive`. A target on another machine reaches the listener through a TLS-terminating proxy or tunnel you run, named in `callback.base_url`, which must then be https. The listener answers every request with an empty 204, keeps only time, method and source address of requests that carry a marker, and is never a target of the Verifier itself. If it cannot bind, the run goes on and SSRF findings stay unconfirmed.

**Session cookies (CWE-614, 1004, 1275).** The scope's [`session_checks`](#scope-file--scopeyaml-authorisation-ver-001) names the cookie and a harmless GET that issues it. The agent declares a `session` plan with that entry and repeats the observation. CWE-614 checks Secure, CWE-1004 HttpOnly and CWE-1275 SameSite (Lax or Strict). An absent, expired or ambiguous cookie stays `inconclusive`. Cookie values never reach the model or the report. Session fixation, logout, expiry and token validation are not inferred from these attributes; they need separate checks.

**Negative verdicts and confidence.** Negative verdicts also need evidence. Without an answered request the result is `not-attempted`. Injection needs boolean experiments on one input in at least two declared contexts, such as a numeric and a quoted one, each checked against its own plan: the baseline answers 2xx with the same content each time, and the true and false controls, each repeated, answer alike, 2xx with one observation that is not the sent value echoed for `not-reproducible`, or one repeatable rejection (400, 403, 406 or 422) for `blocked-by-control`. A context is the declared template or the control pair the agent chose. The controls need not reproduce the baseline: an input the target turns into a non-matching value answers both alike. An observed `text` must stand in every baseline answer and in no control answer, so it shows a result rather than the page. A timing or engine-error experiment supports no negative verdict. The report names the contexts and that a syntax error the target answers like an empty result is not excluded. Access control needs the declared resource visible to its allowed role and absent for an independent denied role; a 403 or 404 supports `blocked-by-control`. A timeout, scope refusal, missing capability or server error establishes no control. XSS needs a completed browser attempt that carried the marker parts; for the other marker classes an unsuccessful attempt stays `inconclusive`. Confidence is set by the check: `medium` for injection and checked negative results, `high` for other confirmed proofs, `low` for unresolved or unattempted findings. Every checked result and exported annotation states that it covers only its cited requests and variant.

### Proof of concept and evidence (VER-034, VER-035, VER-059)

Every finding the agent tested gets a proof of concept, whatever the verdict, also when a limit stopped it. Each request an agent step sent to the target is recorded with its response: `http_request` gives one exchange (two when it renewed a session after a 401), `browser_check` every request of the page that the Verifier answered, with bodies only for documents, XHR and fetch. They are written to `evidence/<finding>-poc.har` (HTTP Archive 1.2, owner-only), which Burp, ZAP or a browser's developer tools can import. Each entry names its step (`_step`), and `_decisive` marks the steps the verdict rests on: for a confirmed verdict the steps its proof check used, for XSS also the `browser_check` in which the marker executed and for SSRF the request that reached the listener; for any other verdict the steps it cites in `proof_steps`. The model sees none of this beyond its own tool results.

The report lists every step in one line, a `browser_check` with the page it opened, and shows the decisive ones as HTTP excerpts: the request line with `Authorization` and `Content-Type` and up to 350 characters of the body, and of the response the status, a few headers and the part of the body that decides. A body of up to 600 characters and 12 lines is shown whole. A longer one is cut to a window around the part that decides (the marker file's content, the XSS marker, the engine error or generated marker an injection proof reads, the first difference between two injection answers, otherwise the start). A long JSON body outside injection shows only its marked fields and fields such as `id`, `UserId` and `role`, and a long HTML page its visible text. For XSS the page source is left out when the marker is not in it, because the browser's observation decides. ⟦…⟧ marks the decisive parts; the HAR keeps the exchanges unmarked. Where the test agent's presentation is used (below), the excerpts, their order and the marks are the agent's instead.

**Test agent's presentation.** With its verdict the test agent composes how a reader sees the proof of concept: every step the verdict rests on in reading order as `Normal request`, `Attack`, `Outcome` (what the attacker obtained, only for a confirmed verdict) or `Control`, each with a plain label and, where the answer shows it, an excerpt of that answer of at most 12 lines; up to three marks on a request or an excerpt, each with a label saying why it matters; and one sentence on what the attacker sent and obtained, or for any other verdict what the steps show and what is missing. The Verifier uses it only if every excerpt is a verbatim part of the step's recorded, redacted answer (whitespace aside; for a page also its visible text and for JSON its serialised form, but then without `<`, `>`, `&` or quotes, which those forms show decoded), every mark stands in the URL-decoded request or in the excerpt shown, every request the verdict rests on is listed, no excerpt quotes an answer withheld from the model or not kept (engine-error probe, login-bypass control, comparison without credentials), and no step of an unconfirmed verdict is an outcome. A presentation that fails a check goes back to the agent once with every reason, which costs one model call; only the presentation of its answer counts, so the checked verdict stands whatever else that answer says. If the second one fails too, or the agent gave none, the Verifier shows its own presentation as described here, and the report and the image say why. The report prints the agent's sentence as `Test agent's account: …`, each step's label as `Test agent: …` and each mark's label after the marked text, in code fences, because they are model text and never proof.

Before an exchange is recorded, headers the identity added read `[identity <role>]`. The following read `[redacted]`: the values of `Authorization`, `Cookie` and `Set-Cookie` (cookie names and attributes stay), of other headers whose name contains `token`, `secret`, `passw`, `api-key`, `session`, `credential` or the word `auth`, of query parameters named that way, and every JWT; every credential value the run knows reads its placeholder (see [Identities file](#identities-file--identitiesyaml-sessions-ver-016028040)). Bodies are kept up to 256 KiB each after redaction and up to 4 MiB for all bodies of a finding, binary bodies only with type, length and hash. Other data the target returned stays, because the proof needs it; `export` never references the HAR file.

**Application screenshots.** For confirmed findings with a visible application effect, an available application screenshot leads the visual explanation, and the recorded HTTP exchanges always accompany it. The technical proof determines the verdict. In the report, application screenshots come before the HTTP details. For XSS it is the page where the marker executed. At the top the screenshot shows the URL as requested in an address bar, below it the dialog the payload opened with the marker as its text, drawn from the recorded call because a browser's own dialog never appears in a page screenshot (the image says so), then the section of the page around the payload element, at least 280 pixels high, with the element outlined in red, and below the page a caption with the finding, identity, status, time and payload element. Whatever of the page covers the payload element, such as a dialog and its backdrop, and floating layers that do not contain it, such as notifications or confetti, are hidden for the screenshot and named in the caption and in the event record; a bar along the top edge, such as the application's header, stays.

The agent shapes this evidence. Where a page of the application can show the effect, it may choose test inputs whose effect is visible there, such as XSS that also writes visible text; anything stored still carries the finding's marker. For confirmed access-control and injection findings the agent may pick a UI route and up to three values from a decisive step's response to show. The browser opens that route once, read-only, under one of the run's identities, and saves the screenshot only when the same resource is read successfully and a selected value appears on the page; this also covers the owner's read-back of a confirmed write. These requests count against the scope and run limits, are added to the HAR, and never repeat the write or change the verdict. The image identifies the viewing role and the recorded proof step; an owner's view of a changed record shows the effect, not the attacker's ability to read it. For any confirmed finding, XSS included, the agent adds one sentence on what the leading screenshot shows, which the report prints under the image as `Test agent's explanation: …`; it is never proof. If no UI route is known, the browser cannot show the effect, or screenshots are off or unavailable, the report says so. API-only findings use the HTTP exchanges as their evidence; the Verifier does not make up a UI for them. Selecting all screenshot classes enables their supported captures, without requiring an application view for every class.

Before a live screenshot is captured, known credential values are replaced with their placeholders in readable page text, form values and text attributes. Captions and the displayed URL are redacted too. The image and report identify this masking. The page is frozen for presentation and its text is checked again after masking and annotations; masking sends no requests and changes neither the recorded exchanges nor the technical proof. If masking would remove a selected proof value, the page restores a credential, a credential remains in unmaskable text, or the text cannot be checked, the image is omitted and the report states why.

**Access-control pages.** For a confirmed access-control finding, each decisive response that is an HTML page is rendered in the proof browser from the recorded, redacted response, without a new request. Only the page itself is answered; images, styles and scripts are aborted and scripts are off, so the page may look unstyled. The caption names finding, step, request, identity, status and time. Up to three values the model names in `highlight`, such as the other identity's email, are marked in yellow where they occur in the response, and the caption says what is marked.

**HTTP screenshots.** Every tested finding gets `evidence/<name>-http-<n>.png` (names: see [Outputs](#outputs)) when `--screenshots` includes its class, also beside the page screenshot of an XSS or an access-control page. These images, like the explanation panels of the evidence review, stay in `evidence/` for later use and are not embedded in either report. With the test agent's presentation the image shows the finding and verdict, the agent's sentence marked as its words, the proof check's result, and then each step as the agent arranged it, request URL-decoded beside the status and the excerpt, with the agent's marks and labels and, where the proof reads one from the step, the Verifier's own observation of it. Otherwise the Verifier composes the image as follows, and its header gives the reason. They show the steps the verdict rests on; when the verdict cites none, for example because a limit stopped the finding, they show the answered requests after the last test plan, and the header says the image proves nothing. Request and response stand side by side as recorded and redacted, rendered in the proof browser without a new request, with up to two exchanges per panel and at most three panels. Where the accepted test plan or the finding's payload says what a step is, its heading names it: `Normal request` (green: the baseline input, the identity the resource belongs to or is allowed for, a request without the payload), `Control` (grey: a request without login), `Attack` (red) or `Effect` (orange: the owner's read after another account's change). A panel then shows a normal request on top and an attack below, one panel per kind of attack, and a highlighted line under the attack compares its answer with the normal request above, for example `same status 200, the identical answer`. A boolean injection experiment is shown as its proof compares it: per form the true condition below the false one and compared with it, then the true condition below the baseline. If the true and false condition answer differently in a way the proof does not count, the line says so with the proof check's reason, for example `the complementary true predicates did not produce the same observation`. For an injection experiment the response shows the value the experiment observes instead of the raw body, a list as one entry per line with `+` before each entry the compared answer does not contain. A step that neither the plan nor the payload places gets no role. JSON is formatted, HTML error pages show their visible text, and routine headers and unrelated HTML are left out; the HAR keeps the complete exchanges. Above the steps each image says in three lines what the test did (`Test:`), what the steps showed and what the verdict makes of it (`Result:`, for example `baseline input: 2 entries · true condition: 46 entries · false condition: 0 entries. The proof check accepted it.`; a step whose proof reads an observation of its own is named by it instead of its status, such as `syntax break "'": engine error`), and which steps this image shows (`Shown:`); small print names the HAR file and the capture time and what the colours mean. Unsuccessful HTML control responses stay in the panels and get no page image of their own. Marked is what the Verifier can locate, in a request highlighted after a red label (`payload`, `input`, `identity`), in an answer framed in red with a short red note beside it: the identities an access-control proof compares, the XSS or SSRF marker, the redirect host and the `Location` header, the marker file's name and content, the input and the part of the answer that differ between two injection requests (with an experiment, the line of the observed value; with a boolean experiment only where a confirmed result's true condition differs from its false one) and a different status, except for a step whose proof reads an observation of its own, where only that is framed if the answer shows it: the engine error of an engine-error probe, the generated marker of a returned-marker proof, or the selected text or the step's own computed result in a page answer; and the session cookie's `Set-Cookie` line with the checked attribute (`HttpOnly missing`); cookie values stay redacted. In an access-control attack's answer, ownership fields such as `UserId` that equal the normal request's are framed, and the entries an injection answer adds share one frame. The note says why the framed part counts, such as `◀ account-2 gets the same UserId as account-1`, `◀ 46 entries instead of 0` or `◀ HttpOnly missing`. Above each step the image states facts about it, in bold where the verdict rests on them: the decoded injection input, the answer times when they differ by 2 seconds or more, for XSS which page the browser opened (with the payload, also when it sits in the `#` fragment that never reaches the server), and what the proof check reads from the step itself: whether the XSS marker executed, the marker file was read, the listener received the marker (SSRF and out-of-band injection), the answer carried an authenticated artifact (login bypass), the request raised an engine error, the step's generated marker returned, the answer held the selected text, or the step's own computed result stood in it.

The proof browser starts for screenshots only when a finding of an included class is selected; without Playwright or Chrome no screenshot is taken and the verdicts stand. No verdict depends on a screenshot.

### Safe mode (VER-030)

Safe mode is the default. Without `--allow-intrusive` the run sends only GET, HEAD and OPTIONS. It sends the most harmless payload that can still decide a verdict, keeps request count and rate low, and does no wordlist fuzzing, broad parameter sweeps or long series of payload variants.

Write requests (POST, PUT, PATCH), needed for stored XSS and some access-control cases, are sent only with `--allow-intrusive`, not with `--read-only`, and never when a scope file says `allow_state_change: false`. They carry unique markers and are logged (VER-014). The Verifier refuses a write that does not carry the finding's marker (the `vrf…` part named in the model's instructions) in its path or a value, and a write whose path names an existing record: a segment at a placeholder of the route (`:id`, `{id}`, `<id>`), or a segment of digits or a UUID. A write may create, never change what may belong to someone else, such as `PUT /api/BasketItems/1` in another account's basket. A `test_resources` request is sent as declared, and in a write proof the other account may change the record the owner created for that finding (see [Proof per class](#proof-per-class-ver-009-to-ver-013)). Identifiers in a request body are not recognised; the model is told not to name another account's record there. DELETE and every method other than GET, HEAD, OPTIONS, POST, PUT and PATCH are always refused.

Without `--allow-intrusive`, a finding whose named requests all write, or whose variants all list the capability `state-change`, is not tested; the test plan lists it under "intrusive mode" with `run with --allow-intrusive`. In a terminal, the test agent can ask you for a write it comes upon during a test instead of giving up, when it declares a plan or sends a write that only intrusive mode allows (VER-052). A write the finding names before the run is refused in safe mode without a question, whether the agent plans it or sends it, because the test plan already showed it: a variant's request, a request the assessment names for the finding or that prepares its test, and an injection input with a JSON or form body or a test resource the scope file declares for it. The same holds for a plan on a variant that lists `state-change` and for an access-control plan for which an account creates its own record (see [Proof per class](#proof-per-class-ver-009-to-ver-013)). The question shows the finding, the write requests, the identity, that anything a write creates stays on the target, and the agent's reason, marked as its claim. `y` allows writes for that finding and `a` for the rest of the run; Enter, any other answer, the end of input or 120 seconds without an answer decline, and the finding goes on read-only. The Verifier asks only for a write it would send with `--allow-intrusive`, at most once per finding, and never with `--read-only`, with `allow_state_change: false` or without a terminal. The waiting time counts toward the run time. The report's mode line names the findings you allowed writes for, and each finding's table gives your answer under `Writes` (`write_permission` in `verification.yaml`).

A POST can still change or remove data, so use intrusive mode only against a test instance you can reset. A reused command line with `--allow-intrusive` writes to whatever target it names, so check the target before you confirm; a `localhost` reached through `ssh -L` or `kubectl port-forward` is a remote system. Created resources normally remain on the target; use their recorded markers to remove them or reset the test instance. Archive tests can use an explicitly declared cleanup endpoint and report whether removal succeeded or manual cleanup is needed.

### Interactive and non-interactive

- Interactive (default, with a terminal): the run prints its settings and waits for one confirmation before the first request (VER-002). A credential variable that is not set is asked for hidden before that, and sign-ins in your browser (`oidc-authorization-code`, `oidc-device-code`) happen after it, before the first finding. Later the run asks only for a higher cost limit when it reaches it (see [Boundaries](#boundaries--cost-and-load-ver-015)) and, in safe mode, when the test agent asks for a write (see [Safe mode](#safe-mode-ver-030)). The guided run (above) asks for the settings first.
- Non-interactive (`--non-interactive` / `--ci`, or no terminal): no prompts. Selection, profile and confirmation (`--yes`) come from the command line; a missing confirmation stops the run. Every credential variable must be set, and an identity that needs a person to sign in stops the run before anything is contacted; use a login program or client credentials there.

### Console output

The console is laid out like AppSec Analyzer's, with a red logo and red accents instead of its turquoise. Before the first request `verify` prints its settings as `Key : value` lines: the assessment, the selection with its severity floor, the target with its scope and owner (or `no scope file`), the mode, the profile and model, and the limits. The guided run shows the assessment once at the start, with how many of its findings are runtime candidates and their severities, and does not repeat it in the settings. For selected classes that need a preparation and have it, one more line names it: `Identities` (roles only; with `--account` the `Accounts` line names them), `Browser`, `Callback` and `Marker file` (its path only). The `Report` line names the Markdown report `verification.md`, next to which `verification.yaml` (YAML, for tools, `--resume` and `export`) is written, and says `replaces` when `--overwrite` replaces a report already there. Then follow the test plan and the question `Proceed against this target? [y/N]`, or `[Y/n]` in the guided run.

During the run, `verify` prints one entry per event on standard error, in the columns `TIME FINDING EVENT PROGRESS ELAPSED LEFT DETAIL`, as AppSec Analyzer does, with a blank line between findings. FINDING is the finding under test and its position among the findings this run verifies; findings that cannot be tested in this run are not counted, and the variants of one finding share its number. PROGRESS is the share of findings done, a finding counting once its last variant is, and ELAPSED the run time. LEFT is estimated from the findings done so far and never exceeds what `--max-duration` leaves; before the first finding is done it shows that remainder (`≤29m`).

| EVENT | Shows |
| --- | --- |
| `start` | The finding's title, severity, class and up to two requests from the test plan. |
| `agent` | `▶ test agent started` with the model in short form and its runtime (`Sonnet 5.5 via Claude CLI`), its steps (`≤12 steps`, set with `--max-attempts`), the identities it may act as, and `source code` with `--source`; `■ test agent finished` with its steps and time. A finding not tested because an earlier one reached a run-wide limit has no `agent` entries. |
| `·` | A request, browser check or source read of the agent: its note on what the step checks, the request with its query and JSON body, the result, how long the model took to propose the step (`model 14s`) and, when costs are shown and model calls cost something since the last amount, the run's spend so far (`run $0.42`), not what the step cost. A result a proof needs (`script executed`, `marker file read`, `callback hit`) is green. |
| `↻` | A step the Verifier refused. |
| `⚠` | A limit that stopped the finding (`stopped by limit: …`), or a test agent stopped after failed actions in a row (`stopped: …`, with the last failure). |
| `proof` | The proof check after the agent finished: green `✓ proof checked` with what the proof showed and the steps it rests on, or yellow `✗ no proof` with what the check missed, the limit that stopped the agent, or the agent's rationale. While steps are left, a rejected confirmation shows `✗ proof not accepted: …` and the agent continues. |
| `rating` | A [rating after verification](#annotated-copies-ver-027-ver-038-ver-039) that differs from the Analyzer's, e.g. `severity Medium → High · likelihood Low → High · confirmed with a checked proof`; shown also without `--annotate`. |
| `done` | The verdict in bold with a mark (`✔ confirmed`, `✘ not reproducible`, `✘ blocked by control`, `? inconclusive`), the time the finding took, when costs are shown the run's spend (`run $0.42 of $10.00`), and for a confirmed finding the first sentence of the agent's rationale. |

Under the `done` entry, one line per screenshot names where it lies (`screenshot verification/evidence/T-036-dom-xss-in-search-results.png`), with the EVENT `proof` when the Verifier checked the verdict's proof, otherwise `img`. The evidence review adds its own entries (see [Evidence presentation review](#evidence-presentation-review)). When a Claude CLI call fails, the reason names the CLI's error kind where it reports one, e.g. `host_error (error_max_turns, exit 1)`. Text from the assessment, the model or the target is shown without control characters and without credential values.

In a terminal the title is bold, the tested request stands on its own row in its own colour under the note, the rationale stands under the verdict, and amounts are highlighted. Lines are at most 140 columns wide, as in AppSec Analyzer, also in a wider terminal; a longer entry continues under its column. A status line underneath shows a progress bar, the run's spend so far when costs are shown (`$0.42 of $10.00`), the running step (`Sonnet 5.5 plans` during a model call, otherwise the request) and its age. Without a terminal each entry is one line, and a line with the status follows after two minutes without output.

Costs are shown with API billing (`codex`, `anthropic-api`, and `claude` with `ANTHROPIC_API_KEY` or a login that bills the API), and with `--show-costs` in any mode, as in AppSec Analyzer. With a Claude subscription the amount is what the calls would cost at API prices and is marked `at API prices`; with `codex-cli` and `copilot-cli` the `Run` row says `cost not reported (subscription)`.

At the end `Results` lists each finding that can be tested against the app: a mark (`✓` confirmed, `✗` not reproducible, `⊘` blocked by a control, `?` inconclusive, `·` not tested), id, severity, class, result and title, with the reason in one line under it. A finding or variant this run could not test shows what it needs as its result (`needs intrusive mode`) and under it how to provide that (`run with --allow-intrusive`). Confirmed findings come first. A finding one variant confirmed does not list its untested variants, and variants with the same result and reason share one line that counts them. `--print` lists every finding, unsupported or incomplete ones included, with the whole reason. A `Run` row gives run time, model calls, requests and, when costs are shown, the spend against `--cost-limit`. `Done` then gives the paths of the report, its data, the evidence, the action log and, with `--console-log`, the console log, and the count per result.

When a run cannot start or go on, `verify` says so on standard error in one form: a line marked `✗` with what is wrong, the details under it, a line marked `→` with what to do, and `Nothing was contacted.` when that is so.

On a terminal the output is in colour and starts with the logo. A confirmed finding is green; not reproducible or blocked by a control is red, which suggests a false positive; inconclusive is yellow. Severities and pre-flight results have their own colours. `NO_COLOR` (any value) turns colour off, `FORCE_COLOR=1` turns it on without a terminal, and `COLORTERM=truecolor` selects the 24-bit palette. Without a terminal, for example in CI or when redirected to a file, the output is plain text.

**Exit codes.**

| Code | Meaning |
| --- | --- |
| `0` | All selected findings were tested, whatever the verdict. A confirmed weakness is a successful run. |
| `2` | The run was blocked before testing: malformed assessment, unreadable, invalid or expired scope, unset proxy or identity variable, unusable model profile, missing confirmation, unreachable target, rejected login, failed model test, empty selection, no selected finding testable in this run, a report already in `--output` without `--overwrite` or `--resume`, a `--resume` report that cannot be continued, or, without `--output`, a run directory that cannot be created. |
| `3` | A limit was reached for at least one finding, for example the cost limit, the request limit, the steps per finding, or the end of the scope window. |
| `130` | Interrupted with Ctrl-C. A `verify` run that had started testing writes its report with the results so far. |

## `preflight` — check before a run (VER-032)

```
appsec-verifier preflight --assessment ./security-assessment.yaml --scope ./scope.yaml \
  [--url URL] [--identities ./identities.yaml] [--source DIR] [--profile P] [--model M] \
  [--offline] [--json] [--yes] [--non-interactive] \
  [--test-model (--cost-limit USD | --max-calls 1) [--show-costs]]
```

Runs the checks `verify` runs before its first finding and tests no finding. Each check prints one line: `✓` passed, `⚠` works with a caveat, `✗` failed, `·` not checked or not applicable. `--account`, `--admin-account` and `--login-url` work as in `verify`; with `--offline` the login endpoint is checked without asking for passwords.

| Check | What it does | Contacts |
| --- | --- | --- |
| Assessment | Checks the fields the Verifier reads against `schemas/assessment.schema.yaml` and that finding ids are unique. Shows project, date, and how many findings are dynamic, static-only or input-incomplete. Messages name the place and the rule; only a repeated id is quoted, escaped. | nothing |
| Scope | Schema, window, URL inside the scope. | nothing |
| Proxy | The proxy URL is http(s) without inline credentials, and `username_env` and `password_env` are both set. | nothing |
| Identities | Schema, every `*_env` variable set (asked for hidden at a terminal, except with `--offline`), endpoints and `check_url` inside the scope, login programs found, and sign-ins that need a person only at a terminal. | nothing |
| Programs | The login programs the identities start, as written. They run at the login check below, with your rights. | nothing |
| Source | Only with `--source`: the path resolves to a readable directory. Offline; its contents are not read here, and whether the agent finds a finding's code there is not shown. | nothing |
| Test plan | The test plan `verify` shows, for every finding and in safe mode: which findings a run tests, and which it cannot test, grouped by what they need, with how to add it and the lines to copy. Warns when a finding cannot be tested, never fails. Runs only when the checks above passed, and is printed after the checks, before the result. | nothing |
| Model | The profile resolves (CLI present and logged in, or key set; model known and priced). For `codex` and `anthropic-api` one metadata request shows the key is accepted and the model offered; it generates nothing and proves no quota. | the provider (not with `--offline`) |
| Target | One GET to the URL through the scope check and the declared proxy. A redirect is not followed. Any HTTP answer counts as reachable; 5xx warns. A failure names its cause: name resolution, refused connection, timeout, TLS certificate or handshake, proxy refusal or proxy authentication (407), or an address the scope refuses. | the target |
| per role | One login for `form`, OIDC and `command` identities, never retried; for `oidc-authorization-code` and `oidc-device-code` you sign in now. With `auth.check_url`, one GET there with the identity's credentials: 2xx accepted, 401 or 403 rejected, anything else unclear. `bearer`, `basic` and `session` without `check_url` are reported as not checked against the target. Two roles whose tokens name the same account (the same `iss` and `sub`) fail, because an access-control proof needs two independent accounts; sessions that do not name their account, such as cookies, are not compared. | target, login endpoints, login programs |
| Model test | Only with `--test-model` (`verify` always runs it, within its own limits): one fixed prompt without target data, findings or credentials. Passes when the host stays confined and replies with exactly the requested step. | the provider |

The offline checks run first; if one fails, nothing is contacted. The target and login checks run only after one explicit confirmation (VER-002), at the prompt or with `--yes`. `--non-interactive` without `--yes` contacts nothing and fails. A failed target check skips the logins.

`--test-model` needs its own limit: `--cost-limit` of at least USD 0.01 for `claude`, `codex` and `anthropic-api`, `--max-calls 1` for `codex-cli` and `copilot-cli`. It cannot be combined with `--offline` and runs only when all other checks passed. Its line shows the call's cost under the same rules as `verify`.

`--json` prints `{"kind": "preflight", "ok": …, "verification": "not_run", "checks": [{"check", "status", "message"}]}` on stdout, and the progress lines and the test plan on stderr. It never prompts, so contacting the target needs `--yes`.

Messages never contain a secret, a token, a response body or a raw error text, which can hold proxy credentials (VER-016). Exit code `0` when no check failed, `2` otherwise.

## `scope` — resolve and check a scope file

```
appsec-verifier scope --scope ./scope.yaml [--target URL]
```

Validates the scope against `schemas/scope.schema.yaml`, prints the resolved boundary (host, ports, path prefixes, window, owner), and, with `--target`, reports whether that URL is inside it. Contacts nothing (VER-001).

## `export` — hand verdicts back to the Analyzer

```
appsec-verifier export --verification ./verification/verification.yaml \
  --output ./verification/analyzer-verification.json [--format json|yaml]
```

Converts a finished `verification.yaml` into verdicts keyed by finding id and the cross-run `match_key` (VER-007), meant for AppSec Analyzer to mark findings with their verification status. The Analyzer does not read this file yet. It never changes or re-scores the assessment (VER-021), contacts nothing and makes no model calls. Default output: `analyzer-verification.json` in the working directory, as JSON. A file that cannot be read or does not match `schemas/verification.schema.yaml` stops it with exit 2.

## `update` — update the installed Verifier (VER-033)

```
appsec-verifier update
```

- Reinstalls the Verifier from the source pipx recorded at install time, such as GitHub or a local checkout. Credentials in a recorded URL are not shown.
- Shows the installed version and the source, then asks `[Y/n]`. Enter or `y` confirms; anything else, or closed input, installs nothing.
- Runs `pipx upgrade --pip-args=--force-reinstall appsec-verifier`, which you can also run yourself. `--force-reinstall` reinstalls even when the version number is unchanged, as is usual between GitHub commits. Like a new `pipx install`, it takes the newest dependency versions `setup.py` allows, not the pins of `requirements.lock`; packages added with `pipx inject` stay.
- Hides the pipx output and shows it only when the update fails (exit 2).
- Afterwards shows the new version as `appsec-verifier --version` prints it from the new installation: the engine version with commit and date of the build, e.g. `0.1.0a1 (a26a8e10, 2026-11-07)`. `(unchanged)` means the source had nothing newer.
- Needs an interactive terminal outside CI (`CI` set); no option skips the question. Otherwise it exits 2 and names the pipx command to run yourself.
- An installation without pipx (a venv from `requirements.lock`, an editable checkout) is not changed; update it the way you installed it.

To switch the source, run `pipx install --force` with the new source. A checkout installed with `pipx install --force .` stays the source: change it, for example with `git pull`, and run `update`.

`--version` names the build: commit, date and local changes, stamped at install time. A checkout without a stamp is read from Git, and a build without either shows `(commit unknown)`.

## Configuration files

### Scope file — `scope.yaml` (authorisation, VER-001)

The scope file states what the Verifier may contact, during which window, and who is responsible. Schema: `schemas/scope.schema.yaml`; examples in `examples/`. A minimal scope needs `schema_version`, `base_url`, `window` and `owner`; the README's quick start shows one.

Without a scope file, `--url` alone is the scope for that run: the URL's scheme, host and port, the whole host. Write requests need `--allow-intrusive` either way. You need a scope file for anything more: several hosts or ports, path prefixes, `deny_paths`, a host name that resolves to a private address (`networks`), a proxy, login hosts other than a `--login-url`, an SSRF callback for a target that is not on `localhost`, the marker file, test resources, injection inputs, session checks, or a test window and owner on record.

| Key | Meaning |
| --- | --- |
| `base_url` | Absolute http(s) URL of the target. Hosts and ports default to those of this URL. |
| `hosts`, `ports`, `schemes`, `path_prefixes` | What may be contacted. `schemes` defaults to the scheme of `base_url`, so plain http is allowed only when `base_url` or `schemes` names it. |
| `deny_paths` | Paths that are never contacted, compared regardless of case and percent-encoding. |
| `networks` | CIDR ranges of private or loopback addresses that may be contacted (see below). |
| `window` | Authorised test period (`from`, `until`, ISO 8601 UTC). |
| `owner` | The person or party responsible for the test. |
| `expected_build` | *Not implemented; the key is accepted but not checked.* Commit or version of the build the assessment was made for (VER-003). |
| `allow_state_change` | `false` forbids write requests: a run with `--allow-intrusive` stops before anything is contacted. Absent or `true` leaves it to `--allow-intrusive` (VER-030). |
| `auth_hosts` | SSO, OIDC and token endpoints that may be contacted only to log in, never tested. |
| `proxy` | HTTP(S) proxy for target and login traffic; credentials are named as environment variables (`username_env`, `password_env`), never in the URL. `no_proxy` lists hosts reached directly. |
| `callback` | Listener for SSRF proofs; `expect_rejected: true` states that the target must not fetch it (see [SSRF](#proof-per-class-ver-009-to-ver-013)). |
| `marker_file` | Path and token of the marker file for path-traversal proofs. |
| `test_resources` | Known harmless resources for access-control checks, each bound to a finding, a concrete request, allowed and denied roles, and an expected response marker. |
| `archive_checks` | Operator-declared disposable archive test locations and optional cleanup endpoints, per finding (VER-045). |
| `injection_inputs` | Inputs that must treat their value as literal data, per finding; needed for injection proofs. |
| `session_checks` | Session cookies to check, each with a harmless GET that issues it. |

For access-control checks, create a harmless resource in the test application and declare its ownership. This example states that `customer-b` may read `/rest/basket/2` and `customer-a` must not receive its marker:

```yaml
test_resources:
  - id: basket-b
    finding_id: T-001
    path: /rest/basket/2
    method: GET
    allowed_roles: [customer-b]
    denied_roles: [customer-a]
    pointer: /test_marker
    value: verifier-owned-basket
```

Use the actual finding ID, path, roles and a non-sensitive marker from your test setup. `pointer` selects a JSON response field in JSON Pointer syntax. An empty pointer checks a literal text marker instead, which must not occur in the request. `anonymous` names a caller without credentials. Optional `params`, `json` or `form` bind fixed inputs; choose one body format. Role lists must be disjoint, and the resource must be inside the target scope. These entries state expected access; they allow no additional requests. Without a `test_resources` entry, IDOR and missing-authorisation findings can also be proven with two accounts and `--allow-intrusive`, or, for a privileged function other than an IDOR, with an `--admin-account`, and every finding except an IDOR by the comparison without credentials with any account; see [Proof per class](#proof-per-class-ver-009-to-ver-013).

For injection findings, declare the input that must treat its value as literal data:

```yaml
injection_inputs:
  - finding_id: T-012
    path: /search
    input_location: params
    input_name: q
    semantics: literal
```

`input_location` is `params`, `json`, `form` or `path`. For `path`, `path` holds the route template with a placeholder (`:id`, `{id}` or `<id>`) and `input_name` is that placeholder's name.

For session-cookie findings, name the cookie and a harmless GET that issues it; omit `role` for an anonymous observation:

```yaml
session_checks:
  - id: customer-session
    finding_id: T-042
    path: /session-status
    cookie_name: sessionid
    role: customer-a
```

Anything outside the scope, whether target, login host or proxy, is refused and not attempted. A path that a server could resolve to another resource (a `.` or `..` segment, `//`, `\`, `;`, or `%2e`, `%2f`, `%5c`, `%3b`, `%25`, `%00`) is always refused. Proxy variables in the environment (`HTTPS_PROXY` and the like) are ignored; only the scope's `proxy` is used.

Addresses are checked when the connection is made (VER-018). Each host name is resolved once, every address it resolves to is checked, and the connection goes to a checked address, so a DNS answer that changes later cannot redirect a request. Public addresses are allowed. Loopback, private and other non-public addresses need `networks`, unless the host is written as that address or as `localhost`. Link-local addresses (including cloud metadata at 169.254.169.254), other known metadata addresses, multicast, unspecified and reserved addresses are never contacted. If any address of a host is refused, the request is refused. Through a proxy only the proxy's address is checked, while target URLs still have to match scope. The operator must ensure that the proxy enforces the destination address restrictions when it resolves and connects to the target. Hosts in `proxy.no_proxy` are checked as without a proxy.

The `window` is checked before every request and every planning step. Once it has closed, the current finding ends `inconclusive` with `limits_hit: window`, no further request is sent, and the run exits with 3.

#### Archive test location

Use only a disposable test area for which you have write authorization. This example assumes `/archive-test/{marker}.txt` serves the parent of `/srv/test-area/extract`, and the cleanup endpoint removes only the named test marker. Without such a mapping the HTTP read cannot establish where a file was written, so leave this finding unresolved.

```yaml
archive_checks:
  - id: zip-traversal
    finding_id: T-027
    upload_path: /file-upload
    field: file
    extraction_directory: /srv/test-area/extract
    read_path: /archive-test/{marker}.txt
    cleanup_path: /archive-test/cleanup/{marker}
```

The cleanup endpoint receives JSON such as `{"marker": "vrf….txt"}`. The report records `removed` only after a successful cleanup response and a 404 or 410 at the read URL. Otherwise use the reported marker to reconcile and remove any test file before another run.

### Identities file — `identities.yaml` (sessions, VER-016/028/040)

Lists the test identities by role name and, per identity, the login `method` and where its credentials come from. The file holds no secret values: it names the environment variables that hold them. Use accounts made for the test, not your own company account, because the run acts with that account's rights. Schema: `schemas/identities.schema.yaml`. Examples: `examples/juice-shop/` (form login), `examples/sso-proxy/` (SSO sign-in in your browser, behind a proxy) and `examples/login-program/` (a login program).

| Method | Session |
| --- | --- |
| `none` | no credentials, for anonymous requests |
| `bearer` | the token in `token_env`, sent as `Authorization: Bearer` |
| `basic` | `username_env` and `password_env` as HTTP Basic |
| `session` | headers copied from a signed-in browser, each from its own variable, e.g. `headers_env: {Cookie: VERIFIER_A_COOKIE}`; also for API keys such as `X-Api-Key` |
| `form` | a login at `login_url`: an HTML login form, whose cookies become the session, or else a JSON POST that returns a token |
| `oidc-password` | the OIDC password grant; meant for test realms, many providers refuse it for accounts with MFA |
| `oidc-client-credentials` | the client-credentials grant, for service identities |
| `oidc-authorization-code` | you sign in in your own browser; needs a terminal and a browser on the same machine |
| `oidc-device-code` | you sign in on any device with a code the Verifier shows; needs a terminal |
| `command` | your login program prints the session |

```yaml
identities:
  - role: user-a                       # sign-in in your browser, MFA included
    method: oidc-authorization-code
    auth:
      issuer: https://sso.example.com/realms/app
      client_id: verifier-cli
      scope: openid
      check_url: https://app.example.com/api/me
  - role: user-b                       # a session copied from the browser
    method: session
    auth:
      headers_env: { Cookie: VERIFIER_USER_B_COOKIE }
      check_url: https://app.example.com/api/me
  - role: user-c                       # your own login program
    method: command
    auth:
      command: [./login.py, user-c]
      headers: [Cookie]
  - role: service                      # client credentials
    method: oidc-client-credentials
    auth: { issuer: https://sso.example.com/realms/app, client_id: verifier-svc, client_secret_env: VERIFIER_SVC_SECRET }
  - role: anonymous
    method: none
```

`form` first reads `login_url`. When the page holds a form with exactly one password field, the Verifier submits it as a browser does on Enter: every named field with its value, hidden fields such as a CSRF token included, checked boxes and the first submit button, with the password in the form's password field and the user name in `username_field` (default `username`) or, when the form has no field of that name, in its only text field. The form must send POST to `login_url` itself; a form that sends GET or posts to another address is not submitted. The Verifier follows redirects within the target origin, sends back the cookies the answers set, whatever their `Domain`, and takes the cookies set during the login as the session, sent as one `Cookie` header, or the token where the answer holds one. The login fails when it ends on the login form again or on an answer other than 2xx. Afterwards the Verifier requests the target URL once with the new session; when that still leads to the login form, the target did not accept the login, for example because it sent it to a setup page, and the login fails too. This check is skipped when the target URL is the login page itself. Settings an application keeps in cookies arrive as the login sets them; DVWA, for example, starts at the security level `impossible` unless it runs with `DEFAULT_SECURITY_LEVEL=low`. Without such a form, `form` sends `username_field` and `password_field` (default `password`) as a JSON POST and takes the token from the answer.

For the OIDC methods `issuer` is enough: the Verifier reads `<issuer>/.well-known/openid-configuration` and takes the endpoints not given as `token_url`, `authorize_url` or `device_url`. Every endpoint must be the target or an `auth_hosts` entry of the scope, also one the discovery document names. Optional fields: `client_id` or `client_id_env`; `client_secret_env` for a confidential client, sent in the body (`client_auth: post`, the default) or as HTTP Basic (`client_auth: basic`); `scope`; `audience`, which Auth0 requires; `resource`, which Entra ID v1 requires; and `token: id` for an application that expects the ID token instead of the access token.

`oidc-authorization-code` needs a client at your identity provider that allows a loopback redirect and issues tokens the application's API accepts. The Verifier prints the authorize URL, opens it in your browser where there is a display, and waits up to 5 minutes for the redirect to `http://127.0.0.1:<port>/callback`. The listener there accepts only that path with the run's `state`, answers that one request and closes. The code is exchanged with PKCE (S256). If the provider needs the redirect registered with a fixed port, set `redirect_uri: http://127.0.0.1:8400/callback` (or `localhost`). The Verifier sends `prompt=login`, so the provider asks again for each role instead of signing the second role in as the first; `prompt: select_account` or `consent` change that. The Verifier never sees your password. This fits applications whose API accepts the provider's token. An application that keeps its own session cookie after the SSO sign-in needs `session` or a login program.

`oidc-device-code` shows a URL and a code, e.g. `Sign in as user-a: open https://sso.example.com/device and enter the code WDJB-MJHT`, and polls the token endpoint at the interval the provider sets, for at most 15 minutes. It also works over SSH. Like the browser sign-in it uses PKCE (S256), so a client that requires PKCE serves both methods.

Both sign-ins happen after the confirmation and before the first finding. A run without a terminal refuses such an identity before anything is contacted.

A login program (`method: command`) covers everything else: a provider that needs a script, a login in several steps, or a CI run. `command` is the program and its arguments as a list; it is run without a shell from the directory of the identities file, so `./login.py` is found next to it. Any language works, e.g. `[/home/me/sso-venv/bin/python, login.py, user-a]`; use your own Python environment for what the program needs, not the Verifier's. The program prints the session on standard output, at most 64 KiB, either one line with a bearer token or one JSON object:

```json
{"headers": {"Authorization": "Bearer eyJ…"}, "cookies": {"SESSION": "…"}, "expires_at": "2026-11-08T14:30:00Z"}
```

`cookies` are sent as one `Cookie` header; `expires_at` (ISO 8601 with a time zone) or `expires_in` (seconds) say when to run it again. Only the header names listed in `headers` are accepted (default `[Authorization]`), and a value with a line break or another control character is refused. `timeout` is 120 seconds by default, at most 900. In an interactive run the program shares your terminal, so it can ask for a one-time code itself; write such prompts to standard error. Otherwise its input is empty. Its standard error goes to the terminal unchanged and is never recorded. It gets your environment without the model providers' credentials (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`). A program that exits with a status other than 0 is reported by that status only and not run again in the run. Otherwise it runs again only to renew the session: shortly before its expiry and once after a 401. The program's own requests are outside the run's scope, limits, rate and safe mode: it runs with your rights, like a command you start yourself. The run lists each program in its settings before the confirmation, and in the guided run a found identities file that starts programs needs its own yes.

Each identity sends its credentials only to the endpoint it names, which must be the target or a scope `auth_hosts` entry (VER-028). The session it obtains is attached only to its own origin, `auth.target_origin`, by default the target base URL; a request as that role to any other origin is refused, and its headers are removed when a redirect leads to another origin (VER-018). The Verifier keeps no cookies the target sets, so a session never travels in a cookie the target set for another identity.

A session whose expiry is known (an OIDC `expires_in`, the `exp` of a JWT, or a login program's `expires_at`) is renewed a minute before it expires: with the refresh token where the flow issued one, otherwise by logging in or running the login program again. When renewing a browser sign-in fails later in the run, that role is unavailable for the rest of it, because the run never asks again. A session from environment variables or a paste is not renewed and is no longer sent once it has expired. When a request is answered 401 again with a renewed session, that identity is not logged in again until one of its requests is accepted. A login the target refuses is not tried again in the run.

Before the first request `verify` checks the file against the schema, that every variable it names is set, that login endpoints and `target_origin` lie inside the scope, and that login programs exist. In an interactive run a variable that is not set is asked for without echo and kept only for the run; without a terminal the run stops with exit 2 and names the variable, never its value. To keep a value out of your shell history, set it with `read -rs VERIFIER_ALICE_PASS && export VERIFIER_ALICE_PASS`. A secret manager can set the variables for the one command, e.g. `op run --env-file=verifier.env -- appsec-verifier verify …`, `doppler run -- appsec-verifier verify …` or `sops exec-env secrets.enc.yaml 'appsec-verifier verify …'`. After the confirmation, configured identities each attempt one login; command-line accounts can try up to two model-selected field pairs (VER-041). A failed login stops the run (VER-032). A `bearer`, `basic` or `session` identity is checked against the target only when it names `auth.check_url`, a URL on the origin its credentials are sent to, which the pre-flight check requests once. Two roles signed in as the same account also stop the run.

Credential and token values are used only to obtain and send a session. They are never written to logs, the report, evidence files or a model prompt; the model addresses an identity by its role name, and recorded requests are stripped of Authorization headers, cookies and token parameters (VER-016, VER-022). A user name is no secret: it stays visible in tool results, logs, the report, evidence and screenshots, so a proof can show which account a page belongs to, unless it equals a secret of the run. If the target echoes a credential, every value the run knows (each variable's value except a user name's, each value entered hidden or pasted, each token, refresh token and cookie value obtained, also JSON-escaped and URL-encoded) is replaced in tool results, the report and the proof of concept by a placeholder that names the account and the kind: `[account-1 password]`, `[account-1 token]`, `[account-1 client secret]`, or `[account-1 session]` for what the account's session obtained. It reads `[redacted]` where that would tell more than that a secret stood there: a value several accounts or kinds share, one that is also a user name, one no account obtained, or one that would appear in a placeholder. Values shorter than 4 characters are not replaced. Before saving a live application screenshot, the Verifier checks the page text, form values and image captions for credentials recognised by the same redaction rules. A detected credential or an incomplete check omits that image and records the reason; the verdict and HTTP evidence remain. The check does not inspect pixels, and retained screenshots are not redacted.

### Test accounts on the command line (VER-041)

For a login that `form` handles, an HTML login form or a JSON POST answered with a token such as OWASP Juice Shop's, you can name the accounts on the command line instead of writing an identities file:

```sh
appsec-verifier ./security-assessment.yaml --target http://localhost:3000 \
  --account jim@juice-sh.op --account bender@juice-sh.op=VERIFIER_BENDER_PASS --admin-account admin@juice-sh.op
```

Each `--account` is a user name, optionally followed by `=VARIABLE`, the environment variable that holds its password. Without a variable the password is asked hidden, e.g. `Password for account-1 (jim@juice-sh.op), hidden:`; without a terminal the run stops and names the account. `--account` and `--identities` cannot be combined, and the same user name given twice stops the run, because an access-control proof needs independent accounts.

The model addresses the accounts as `account-1`, `account-2` and `admin-1` and never sees a password. A user name is no secret: the model reads it where the target shows it, and it stands in your shell history and, while the run lasts, in the process list. The model is told that an `--admin-account` is privileged. Its answers are the reference for privileged functions, and it never creates a resource (VER-010; see [Proof per class](#proof-per-class-ver-009-to-ver-013)).

The accounts sign in at `--login-url`, or else at the one POST entry point in the assessment's `attack_surface` whose path looks like a login (`login`, `signin`, `logon`, `authenticate`, `session`), below the target URL. When the assessment names none or several, the accounts sign in at the HTML login form the target URL shows or redirects to within its origin, and that form may send the password to any address on that origin. The run settings then say `sign in at the login form the target URL leads to`, and after the confirmation the `Login fields` check names the page, e.g. `login form found at /login.php; username/password worked`. When the target URL leads to no login form, no credentials are sent and the run stops; give the endpoint with `--login-url`. Without a scope file, a `--login-url` on another host is allowed for this run only to sign in, and it must be https unless it is on the target or this machine; with a scope file it must be the target or an `auth_hosts` entry. The run settings show the endpoint before the confirmation, e.g. `account-1, account-2 · sign in at POST /rest/user/login (from the assessment)`, with the full URL when the endpoint is not below the target.

After the confirmation, one model call proposes up to two pairs of field names for the user name and the password, from the endpoint and, with `--source`, the handler's source; a login form found from the target URL names its own fields and needs no model call. The model sees no value. Each account then tries at most two pairs, and a pair that worked is used for the other accounts. An HTML login form names its own fields, and they take precedence (see `form` under [Identities file](#identities-file--identitiesyaml-sessions-ver-016028040)). A login that obtains no session stops the run; the account's line names the cause. The session is sent and renewed like that of a `form` login from an identities file.

### Limits — `data/limits.yaml`

Default limits of a run: model cost, model calls, requests, steps per finding, run time and request rate. `--cost-limit`, `--max-calls`, `--max-requests`, `--max-attempts`, `--max-duration` and `--rate` override them per run (VER-015).

## Outputs

Without `--output`, each run writes to a new directory of its own, `<data>/appsec-verifier/runs/<project>/<start time>/`, e.g. `~/.local/share/appsec-verifier/runs/owasp-juice-shop/2026-11-13T14-30-05/`, and never into the working directory. `<data>` is `$XDG_DATA_HOME` or else `~/.local/share` on Linux, `~/Library/Application Support` on macOS and `%LOCALAPPDATA%` on Windows, as for AppSec Analyzer's assessments. `<project>` is the assessment's `meta.project` in lower-case letters, digits and dashes (`assessment` when it names none); the start time is local time, and a run started in the same second as another gets `-2`. These directories are created readable only by you. A run that stops before it writes anything, for example at the confirmation, leaves no directory behind. Earlier runs are kept; nothing removes them. The `Report` line of the run settings and of `Done` names the directory. `--resume` without `--output` takes the newest run of the project whose report is for the same assessment and target, and starts a new one when there is none.

Written to `--output` or the run's own directory:

- `verification.md`: the report. At the top: target, run, mode, scope, authorisation and, when the Analyzer's report lies next to the assessment (its name with `.md`), a link to it. The summary counts the results and lists the tested findings, each linked to its entry, with the result (🟥 confirmed, 🟩 not reproducible or blocked by control, 🟨 inconclusive), the rating before and after verification in the Analyzer's severity colours ([VER-039](#annotated-copies-ver-027-ver-038-ver-039), a change in bold and listed under the table) and one line on what the test showed or why it is not confirmed; then the findings not tested, most severe first, with what the run lacked. Each tested finding follows with a table of result and confidence, rating, CWE and class, technical QA status when available and, with the Analyzer's report, a link to the finding there (shown as `F-005` for `T-005`, as that report names it). Below it: what the checked proof showed, built from its steps and never from the model's words, or why it is not confirmed (what the proof check missed, the limit that stopped it, or the comparison that is missing); the limits of the proof and any deviation; the requests as a table with the steps the verdict rests on in bold; the application screenshot; the proof of concept with request and response of each decisive step in one block, normal requests before attacks, each attack with how its answer compares with the normal request, the true condition of a boolean injection experiment with its false one; and the `match_key` and evidence files. A collapsed appendix holds per tested finding the test plan, the test agent's own explanation, its other observations (not verified), technical QA and the evidence presentation review.
- `verification.yaml`: the same results as data (`schemas/verification.schema.yaml`), each entry linked to its finding by id and `match_key` (VER-007, VER-020).
- `agent-log.jsonl`: written once the target is contacted, owner-only. One JSON object per agent step of every finding, with `time`, `finding`, `step` and either the tool call (`tool`, `args`, `result` with status, body length in bytes, error or the browser's blocked requests; an engine-error probe's answer and a login-bypass control's answer have no length but `body_withheld`, and the probe's `engine_error` shows its class), a refused step (`refused`, `proposal`), a limit that stopped the finding (`stopped`, `reason`) or the `verdict` (VER-017). A record that follows model calls also has `model`: one entry per call with `usd`, what the call cost, and, where the model host reports them, `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and `output_tokens`. The `claude` and `anthropic-api` profiles report the token counts; numbers only, never any prompt or answer text. A finding whose probe failed gets `probe_failed` with the error type and `at` with file and line in the Verifier, never the error message; the finding under test when the run was interrupted gets `interrupted`. It holds no response bodies or source text, and credential values are redacted (VER-016). `--resume` continues it; otherwise each run starts it fresh.
- `console.log`: with `--console-log`, owner-only. What the run printed on standard output and standard error, from the run settings to `Done`, without the live status line; what you type at a question is not in it. It has no colour codes; with `--console-log color` it has the console's colour: `less -R console.log` shows it, an editor shows the colour codes as text. Colour needs a terminal or `FORCE_COLOR=1`, as on the console. A run that stops before it writes a report writes no log. `--resume` continues it; otherwise each run starts it fresh.
- `evidence/`, owner-only: `<finding>-poc.har` for every tested finding, the proof records `<finding>-exchanges.json` and `<finding>-callback-hits.json`, and the images, named after the finding and its title, such as `T-042-product-update-route-has-no-authorization-guard` for "Product update route has no authorization guard — server.ts:369": the application screenshot `<name>.png` of an executed XSS, an application page or an access-control page (more than one: `<name>-2.png`), for an executed XSS marker its record `<name>.json`, the HTTP screenshots `<name>-http-<n>.png` and the evidence review's explanation panels `<name>-explanation-<n>.png` (see [Proof of concept and evidence](#proof-of-concept-and-evidence-ver-034-ver-035)). The title becomes lowercase ASCII words joined by hyphens, at most 60 characters, without the file and line at its end; a finding with variants keeps its variant key after the finding id.
- With `--annotate`: `security-assessment.annotated.yaml` and `security-assessment.annotated.md`, with the figures of the Analyzer's report (see below; VER-027, VER-038).

Recorded responses and retained screenshots can show target data. Live application screenshots are subject to the [credential check](#identities-file--identitiesyaml-sessions-ver-016028040). The report marks them for review before you share them (VER-022). The `export` command writes `analyzer-verification.json` for AppSec Analyzer (VER-021).

### Annotated copies (VER-027, VER-038, VER-039)

With `--annotate` the run writes two copies next to its report. The assessment and the Analyzer's report stay unchanged, also because AppSec Analyzer records a SHA-256 of each file it saved and refuses `export` and `review` of an assessment whose files changed.

`security-assessment.annotated.yaml` is the assessment with a top-level `dynamic_verification` entry for the run (schema version, time, Verifier version, path of `verification.yaml`) and a `dynamic_verification` block on each finding of the report: verdict, confidence, when its result was tested, result id, what the checked proof covers, the rating after verification, and the paths of the proof of concept (HAR) and of the screenshots, relative to the report. A finding is found by its id, and by its `match_key` only when the tested finding has another id in this assessment and no other untested finding carries that key, so a finding that merely shares the key of a tested one gets no block. A finding with variants gets the verdict `verification.md` gives it: the variants' verdict when they agree, confirmed when one of them was confirmed, otherwise inconclusive; its block also lists each variant's verdict and whether every declared variant has a checked result. The block carries no requests, responses, text observed in them or images. Schema: `schemas/annotated-assessment.schema.yaml`. Nothing else in the document changes, so it stays valid against the Analyzer's schema, and the Analyzer's own `verification` field is kept.

`security-assessment.annotated.md` is written when the Analyzer's Markdown report lies next to the assessment under the same name, `security-assessment.md` for `security-assessment.yaml`. It is a copy of that report with three additions. A `Dynamic verification` section before the Management Summary names the target, counts the verdicts and lists each tested finding, by the id the report shows (`F-005` for `T-005`), with the Analyzer's severity and the severity after verification. The changelog table gets a row for the verification run at the top; a report without that table gets the entry in the new section instead. Each tested finding gets a `Dynamic verification` section at its end with the verdict, the rating after verification, the test agent's explanation as plain text marked as not proof, the proof of concept and the screenshots. Findings that were not tested, including those none of whose variants was tested, get no section.

A finding whose anchor in the report is missing or appears more than once is listed at the end of the copy. Figures the report names by a plain file name are copied next to the copy. A report larger than 32 MiB is not copied, and the `Annotated report` line in `Done` says why when no copy is written. When the assessment can no longer be read at the end of the run, neither copy is written and the `Annotated` line says so; the run's own report is written as usual. The copy contains recorded responses and screenshots; review it before sharing (VER-022).

**Rating after verification (VER-039).** The Analyzer's rating stays as it is; both copies show a second one next to it. Severity is the Analyzer's `effective_severity`, else its `risk`. The rules:

| Verdict, with a checked proof | Likelihood | Severity |
| --- | --- | --- |
| confirmed, likelihood below High | becomes High | one level higher, at most Critical |
| confirmed, likelihood High or Critical | unchanged | unchanged |
| blocked by control | one level lower | one level lower, at least Informational |
| any other verdict, or no checked proof | unchanged | unchanged |

Impact never changes. Of a finding with declared variants, one confirmed variant counts, and a block counts only when every variant was blocked. A block covers only the tested requests: a filter that rejects the test payloads lowers the rating although another path may still work, which is why the Analyzer's rating stays next to it. A finding whose likelihood or severity is not one of the Analyzer's levels (Critical, High, Medium, Low, Informational) is not rated. During `verify` the console shows a changed rating as a `rating` entry, with or without `--annotate`.

### Runtime candidates and test preparation

Before testing, each finding is listed as a candidate for runtime testing or as unsupported or incomplete. A supported CWE makes a finding a candidate; it does not mean the run has a suitable proof method and every prerequisite. A CWE without a supported proof method is `unsupported`, not automatically static-only; older reports with `static-only` remain readable. `preflight --offline` reports missing request information, missing test preparation and unsupported proof methods separately.

For access-control findings, the preparation adds, for each record route the finding names (a GET, PUT or PATCH ending in a placeholder such as `/api/Addresss/:id`), the POST that the assessment's attack surface lists for its exact collection (`POST /api/Addresss`), also when the finding itself does not name it (VER-043). A parent path, a sub-route or another method never counts, and no route is invented. The test plan shows the preparation request before the run. It needs two normal accounts and `--allow-intrusive`, and only the owner under an accepted access-control plan can use it, with the usual marker, scope and write checks. Once such a request is answered, the result records it as a deviation (VER-008): `Deviation: the owner created its own test resource with POST /api/Addresss, a route the assessment names for this resource outside this finding (VER-043).` Existing reads, or the existing read of a created record under a change plan, supply the comparison.

## Technical QA (VER-046)

Before a proposed conclusion is final, an independent reviewer checks the finding's hypotheses, attempts, controls, counterexamples and interpretation. A confirmed verdict whose proof check passed is not reviewed; QA runs for negative and unproven conclusions, where it can point at a missing attempt, and continues on a later confirmed verdict only when it already engaged the finding on an earlier conclusion. A confirmed access-control result is the exception: QA judges whether the access it shows is intended by the application, for example a record the application deliberately shares with these accounts. An objection appears beside the verdict, which stays confirmed. One objection alone goes back to the test agent, once per finding and within the shared correction rounds: that the tested resource is meant to be public, such as a public key, while the finding names a protected one. The agent may then test that resource; a checked confirmation on it replaces the earlier one, otherwise the earlier confirmation stands with the objection and the report records how the follow-up ended. QA receives bounded, redacted finding context and recorded steps, including source excerpts the test agent already read, and what a follow-up can still prove in this run: the routes the finding may request, the proof forms open to its class, that a confirmation cites the steps of one experiment and that an injection's negative verdict needs two contexts. It may select up to two additional recorded-response reads, each containing one or two steps and optionally a JSON field or a text window; these contact nothing and cannot read another variant's responses. No credentials, marker-file content or images are sent to technical QA.

The reviewer can return concrete questions to the original test agent for at most two correction rounds shared by all variants of the finding. The agent may answer with existing evidence or perform justified follow-up tests through the same tools. Its history, identities, request and decision allowances, repetition counts and run budgets are retained. A follow-up never grants access to another resource or permission to write. Technical QA uses at most three judgments and two evidence selections, at most five model calls per finding; all count against the run limits. Variants reached after that allowance is used are marked `not-reviewed`.

Only the class's code-checked proof establishes the technical verdict. QA cannot confirm a weakness, waive proof requirements or turn an unperformed test into a negative result. If a follow-up stops at a limit, an already checked result retains its evidence and the unresolved objections. The report's `Technical QA` entry and `technical_review` in `verification.yaml` show the status, review and correction counts, additional response steps inspected and open questions. These counts describe that variant's work within the shared allowance. The annotated Markdown report includes the same entry. Existing saved results keep their recorded review state when resumed. The console and action log show QA feedback and completion separately from target requests; for a result QA objects to, the console line and the report's summary of the finding (`Technical QA objection`) name the first objection.

## Evidence presentation review

After a finding with a confirmed variant finishes, a separate model reviewer checks whether the evidence text explains the scope, identities, comparison and result; a finding without a confirmed variant is not reviewed and records `not-reviewed` with that reason. It also gets the checked proof, the metadata of the application screenshots, including the observed XSS execution, and layout checks done in code, such as screenshot dimensions; an application screenshot larger than 1280 by 1200 pixels is flagged, while HTTP panels, which are saved as files and not embedded, are not. Issues in what the Verifier renders itself, such as the step lines, the facts and marks in the HTTP panels or excerpt lengths, are reported as `readability` and not returned to the test agent, which cannot change them; when only such issues remain, no correction round starts.

The reviewer also looks at the application screenshots the report shows and judges whether a reader sees the exploit or its effect: the marked element or value visible and not covered, enough application context, and caption and agent explanation consistent with the image. It reports image problems as `screenshot` issues. It also looks at the HTTP image of a test agent's presentation and judges whether a reader who does not know the test sees what the attacker sent and obtained, whether each mark sits on what shows it, and whether the agent's sentence claims only what the image shows; for an unconfirmed verdict, whether it says what is missing. These problems go back to the test agent. Only application screenshots and the HTTP images of a test agent's presentation go to the model, at most three per review call, never the Verifier's own HTTP images or explanation panels. A screenshot is sent only if its checked page text, form field values and the text drawn around the image contain no credential value after masking and no content of the scope's marker file. Masking happens before capture; the saved pixels are not edited. An image that fails this check, or whose text could not be read, stays out of the review. Only images actually sent are visually judged; a missing image with a stated reason is not by itself a presentation issue. The images sent can show target data, for example account names, and each costs about 1,000 to 1,500 input tokens per review. All five profiles can send images; `codex-cli` only when its version offers `exec --image`. If a host rejects a call with images, the rest of the run reviews text only. The report lists the screenshots a model reviewed, or says that none was shown, and the console says why.

If the reviewer finds a problem, the original test agent gets the feedback and can add a short explanation with exact quotes from the recorded request or response, or present the proof of concept again. If no excerpts were recorded, it can explain the missing evidence without inventing a quote. When the Verifier composed the HTTP evidence because the agent's presentation was missing or failed a check, that is an issue for the agent even if the reviewer finds none. A new presentation passes the same checks as the first; if it does, it replaces the HTTP images and the report's excerpts, otherwise everything stays as it was and the console's `revise` entry says why. `verification.yaml` keeps these explanations and quotes as explanations, not additional proof; the report leaves them out, because they repeat its proof of concept. With screenshots enabled, a correction also produces a compact explanation panel beside the original evidence; the full HAR and the original images stay. Corrections never change the verdict, confidence or proof check, and they contact the target in one case only: for a `screenshot` issue on a confirmed access-control or injection result, the test agent can choose another UI route for the screenshot. The Verifier opens it once per correction round, read-only and with the same checks; the new screenshot replaces the earlier one only if the page shows a selected value, and its requests are added to the HAR.

Each finding has at most two correction rounds, shared by its tested variants (up to five more model calls per finding), within the run's cost, call and time limits. Repeated issues without improvement, unchanged corrections, invalid responses, cancellation or exhausted limits end the review early. A failed review keeps the technical result.

The console shows `▶ evidence reviewer started` and `■ evidence reviewer finished` with the review status as `agent` entries, the second with the review's time, which the finding's `done` line then leaves out, `review` and `revise` entries for each correction round and, when needed, `issue` entries. `revise` and `issue` entries give the first sentence of the reviewer's text; the report names the variant where a finding has several. A review that never started gets a `quality` entry with the reason. The report's appendix records `clear`, `needs-attention`, `stopped` or `not-reviewed` apart from the technical verdict and the first sentence of each unresolved issue, with its variant where a finding has several; `verification.yaml` keeps the full text, and the annotated report shows the same after each finding's proof of concept. Untested variants are not reviewed. A finding with more than 16 tested variants, or with evidence too large for the review, is reported as not reviewed. The model sees only bounded, redacted excerpts, panel text and the cleared screenshots, never marker-file content or credentials. The answer of an engine-error probe or a login-bypass control appears there with its status line and a notice that it is withheld; the HAR keeps it for you, and so do the Verifier's own image and report, while a test agent's presentation shows only the notice.
